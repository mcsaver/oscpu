# RV64：网页 Pro 架构设计与 Codex 实现验证

本目录保存用户显式选择的协作工作流：网页 Pro 负责主要架构思考与设计，本地 Codex 负责
事实采集、实现和验证。Pro 根据自含的工程证据提出并比较方案，Codex 核查合同并执行实验，
再把关键反证反馈给 Pro。目标是减少无效架构投入；这种分工不预设 Pro 一定更强，
咨询本身也不代表性能改善。

沿用[工作区规范](../../../.github/AGENTS.md)、
[架构入口](../ARCHITECTURE.md)及适用的
[架构/PPA 工作流](../../../.github/instructions/rv64-ppa-optimization-workflow.instructions.md)。
本流程不增加每步批准、通用 gate、全量回归、唯一 shell、新数据库或新的正式签核条件。

## 何时使用

适合以下情况：多个完整架构候选难以取舍；需要跨流水或跨事务生命周期重构；
局部优化连续收益很小；实测与预测明显矛盾；需要独立检查完整候选的收益解释。

已定位的局部 bug、明确的 RTL 实现、编译调试和定向验证，由本地 Codex 连续完成。
用户选择本流程后，同一目标和授权范围内的网页往返不重复询问；只有真实授权边界改变、
目标会话无法辨认或需要用户登录操作时才说明具体缺口。

## 角色与会话

- **网页 Pro：主要架构设计者。** 基于事实提出竞争解释、比较完整候选、选择最值得验证的方案，
  说明跨模块合同、可证伪预测及保留/回滚条件。Codex 不先选好架构方案再只要求 Pro 审查或背书。
- **本地 Codex：事实采集、实现与验证者。** 恢复真实源码、调用链、计数和时序路径，明确 UNKNOWN；
  核查 Pro 的事实前提与接口合同，完成实现、局部 bug 修复和最小充分验证。普通实现选择无需逐项咨询。
- **实测驱动架构回访。** 若证据推翻主要因果解释、方案需要改变跨流水/事务合同，或必须在新的
  CPI/PPA 代价之间取舍，Codex 把事实和反证返还 Pro，由 Pro 重新提出或调整架构方案；
  已定位的实现错误由 Codex 自主修复，不把每个调试步骤变成网页往返。

每轮可以新开网页会话，提交包含当前目标、实现、约束、原始证据和未知项的自含事实包。
用户要求新会话时，不沿用旧对话中的方案讨论；旧实验的实测结果及反证仍可作为标明版本的证据，
原会话与记录保留。新的咨询不默认继承旧推荐，也不把 Codex 的偏好包装为已确定的输入条件。
如果用户已明确指定方案或限制候选范围，事实包如实写明该要求。

## 以完整拓扑交接架构思考

2026-10-08 起采用[可量化设计单元约定](topology-contract.md)：本地提供目标、当前结构、源码与验证事实，
网页主导跨单元的架构变换。拓扑包含流水寄存边界、状态 owner、容量/带宽、同拍资格/信用依赖及取消/副作用，
不只画模块连接，也不预设首选候选。网页可以改变这些边界，而不是只在固定文件中做微调。

发送时采用“简短任务 + 可检索附件”。主拓扑和七个域的拓扑保留全局结构；最差路径连同内部 Q 起点、
相邻关键端点、动态周期及已失败实验一并呈现。这样既减少本地解释对选择的影响，也避免一条极值路径遮住系统代价。
缺少的 latency、吞吐和因果计数标 UNKNOWN，由网页判断哪些值得补测，不为上传要求把所有指标测完。
新会话发送完整结构快照；同一轮后续优先发送变化的单元/接口和新增测量，并明确未变化的基线。
只有上下文已不足、主要结构变化或用户要求新会话时才重新发送全量包，避免把重复阅读消耗当作深度设计。

可运行 `python3 npc/rv64/ai/export_web_context.py` 导出自含材料；默认输出到 `npc/rv64/build/ai-web-context/`，源码范围在导出脚本中明确列出。
导出会对照已测基线的 RTL/header/filelist；若不一致或原快照已清理，会标 DIFFERENT / UNKNOWN，
历史测量不得继续冒称当前成绩。导出本身不自动重审拓扑，也不会覆盖已发送的历史交接附件。
导出不发送任何网络请求。实际上传仍通过已授权的侧边栏浏览器，确认附件已处理、消息已发送和回答已完成；
网页无法读取本地相对链接，因此关键证据与代码正文要在附件里。

## 一次闭环

1. **Codex 整理事实和开放问题。** 确认真实 worktree、用户已有改动、当前 RTL/filelist/config
   与验收目标。提供必要源码、路径、计数及出处，区分事实、历史测量、新测、模型和推断。
   说明待解释现象、未知项和已尝试的负结果，不预先替 Pro 选定方案。
   可使用[咨询模板](consultation-template.md)。
2. **确认并发送到指定网页。** 从实际 UI 确认会话、登录状态、可见模型和推理模式，再通过
   已授权的网页会话发送事实包，请 Pro 提出并比较方案。只包含问题所需的工程内容，
   排除 secret 和无关私密资料。本地子代理或 API 的回答不得冒称网页 Pro；
   看不到模式时记录“未确认”，不根据名称猜测。
3. **取得 Pro 的完整设计回答。** 等待回答完成，保存本次问题与完整回答；记录实际会话链接、
   可见模式、日期和取得方式。若仍在生成、只读到一部分或网页失败，明确标注缺口。
   证据不足时先按其指出的问题补采事实，不用本地预选方案替代缺失的网页设计结论。
4. **Codex 核查并落实方案。** 核查建议依赖的源码事实、接口语义和证据版本。对局部实现问题
   自主处理；事实纠正若改变架构选择，则携带反证回传 Pro。网页意见不能扩张用户授权，
   也不能代替真实 correctness 检查。
5. **执行有界实验。** 依据实际仿真/综合成本落实预算、最小完整设计点、否定和停止条件，
   完成必要原型与最小充分验证。跨模块方案一起评价，允许明确中间态暂时退步；
   不因一次不利结果无限扩大方案，也不把诊断性理想化结果当真实 RTL 成绩。
6. **反馈与裁决。** Codex 汇总可比较的 A/B 结果、局限及反证。需要新的关键架构决定时，
   由 Pro 基于新证据重新取舍；已有保留/回滚条件能够裁决时，直接执行并记录结果，避免重复咨询。
   用“保留、淘汰、证据不足”说明本轮结论，区分工程测量与 Pro/Codex 的解释。

网页思考期间，Codex 可并行进行独立的基线测量、事实探针、验证刺激准备和普通局部修复。
开放架构方案由 Pro 提出后再实现；用于区分事实的可逆探针不等于选定架构方案，
也不构成新的批准或等待 gate。
具体并行顺序按真实 CPU/内存资源安排，例如大网表导出与 STA 避免同时达到内存峰值。
先读取同规模历史任务的峰值内存，区分 RSS 与虚拟地址空间上限；不要为了并行把单个任务限制到
已知需要的内存以下。大网表导出还可能因保存后重读的命名表示增加内存，不能仅按文件大小估算。
若工具在已完成映射后的导出阶段失败，先检查现有完整检查点能否按原命令恢复，保留失败日志；
恢复影响可比性时对基线走同一流程并核对实际面积和时序，不把工具错误当成架构淘汰依据。


每次咨询优先解决一个重要判断；附上当前全核拓扑与必要源码，不发送整个 build 或无关仓库资料。
需要跨模块重构时，应给出相关调用链、数据流和合同，使 Pro 能够独立推导候选，并检查摘要中的假设。

## 工程证据与实验边界

- 当前源码优先于历史说明；历史测量只对其对应版本成立。当前有未提交修改时，明确其影响，
  保留用户改动，不把分支名相同当作版本相同。
- A/B 的功能、周期、综合和 STA 结论应来自可比较的 RTL/filelist/config/workload/tool/corner；
  约束或输入不同要单独说明。收益不能拼接不同历史设计点的有利数字。
- 完整程序、局部吞吐、模型上界和物理实现分别报告；CPI 下降不自动等于真实运行时间下降。
- 物理重构选型同时考察目标输入、下游输出和其他接近全局最差的路径。需要解释最差端点迁移时，
  优先复用已有网表比较同语义端点；不同寄存边界的局部slack不能相加成整核收益，
  “最坏端点换了”本身也不解释退化原因。第二轮实测及淘汰原因见下方实验报告。
  模式确认或网页通信通过，不代表架构正确性、性能、PPA 或系统验证通过。
- 跨模块合同至少说明状态归属、握手/信用、取消与恢复、异常顺序、不可撤销副作用及晚到响应。
  适用时读取[接口合同规范](../../../.github/instructions/interface-contract-first.instructions.md)。
- 预算以现有运行耗时、资源和问题价值为依据，采用时间或昂贵实验次数等可观察单位；
  模板中的空项按当前任务填写，不硬编码统一阈值。
- 每个完整候选提前说明联合修改范围、补偿关系、完成条件、回退点和停止条件。
  只验证实际改动影响的范围；正式 release/PPA promotion 继续使用仓库既有规范。
- 测量推翻假设也可以结束本轮。保留反证及原因，避免以后重新投入同一个无效方向。

## 测试验收

分别报告下列结论，不能用其中一项代替其他项：

| 项目 | 完成证据 |
| --- | --- |
| 文件落地 | 工作流与模板存在、内容可读、相对链接正确 |
| 网页发送 | 真实目标会话、UI 可见模式以及本次实际发送内容 |
| 网页接收 | 已完成回答的全文和会话来源；若截断则未完成 |
| 本地核查 | 对关键事实和建议的源码/证据核对，列出接受、纠正或待实验项 |
| 本地实验（若执行） | 命令、输入/配置、返回状态、可复核结果及实验能支持的结论 |

首次连接测试可以只验证文件、发送、接收和核查；是否运行 RTL 实验由本轮实际目标决定。
如果未改 RTL、未跑新性能测量，就明确写“未证明 RTL 性能提升”，不为测试通信而启动昂贵全量回归。
