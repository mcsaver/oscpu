# OoO Branch Spec Tracker

## Stage 1 - Requirements

- `OooBranchSpecTracker` owns only the front-end branch-speculation checkpoint state:
  `active`, `checkpoint_pending`, and `pred_pc`.
- The parent still owns branch resolve comparison, checkpoint capture predicates,
  PC/outstanding sequencing, FIFO seed/clear, pending branch payloads, BPU/RAS
  update, trap/CSR recovery, and backend issue blocking decisions.
- Inputs are single-cycle event predicates generated by `OooFrontend`.
  Outputs are registered state observed by the existing frontend gates.
- `rst || flush_i` clears all state. A precise CSR/trap clear also clears all
  state and must win over same-cycle capture/start events.
- Out of scope: changing branch prediction policy, re-enabling the dead
  checkpoint capture path (`direct_branch_spec_start_w` is now tied to
  `OOO_ROB_WALK_MODE`=1 in the glue, but `checkpoint_capture_i` is constant
  zero), or moving PC redirect state.

## Stage 2a - Protocol Rules

- The module is a fixed-latency synchronous state owner. There is no backpressure
  or valid/ready handshake.
- `direct_frontend_flush_i` may start a new checkpoint-pending entry only when a
  direct branch fires, the direct branch was not already redirected, and
  `direct_branch_spec_start_i` is asserted.
- `checkpoint_capture_i` promotes a pending checkpoint to active only when
  `direct_frontend_flush_i` is low, matching the parent priority that direct
  flush suppresses capture in the same cycle.
- `resolve_valid_i`, `pending_branch_commit_resolve_i`,
  `pending_branch_match_clear_i`, and `branch_resolve_untracked_i` clear the
  state. The untracked clear is also suppressed by same-cycle direct flush.
- `csr_trap_clear_i` is modeled as the final precise recovery priority by
  clearing immediately for the cycle; same-cycle capture/start cannot survive it.

## Stage 2b - State Machine

| State | Encoding | Meaning | Exit |
| --- | --- | --- | --- |
| `IDLE` | `active=0, checkpoint_pending=0` | No branch-spec window exists. | Direct branch spec start creates `CHECKPOINT_PENDING`. |
| `CHECKPOINT_PENDING` | `active=0, checkpoint_pending=1` | Direct branch has selected a predicted PC and waits for backend checkpoint capture. | `checkpoint_capture_i` enters `SPEC_ACTIVE`; recovery/resolve clears. |
| `SPEC_ACTIVE` | `active=1, checkpoint_pending=0` | Backend checkpoint exists and younger ALU-only work is speculative. | Resolve, commit fallback, untracked recovery, trap, reset, or flush clears. |

Illegal encoding `active=1 && checkpoint_pending=1` is not generated by the RTL.

## Stage 2c - Invariants

- `active_o && checkpoint_pending_o` is never true. Violating it would make
  recovery logic treat the same branch as both not-yet-captured and captured.
- `pred_pc_o` is written only by a direct branch spec start and is cleared on all
  recovery exits. During `SPEC_ACTIVE`, it is retained for restore comparison.
- `csr_trap_clear_i` clears all state in the same clock edge regardless of any
  lower-priority event.
- Direct flush suppresses checkpoint capture and resolve events in the same
  cycle, preserving the existing parent ordering.
- The module never writes pending branch payloads, PC state, FIFO state, BPU, RAS,
  CSR, or architectural commit state.

## Stage 2d - Datapath Constraints

- State registers: `active_q`, `checkpoint_pending_q`, `pred_pc_q`.
- Start mux: `direct_branch_fire_i && !direct_branch_resolve_redirect_i &&
  direct_branch_spec_start_i` selects `direct_branch_pred_pc_i` into `pred_pc_q`.
- Clear mux: reset/flush and `csr_trap_clear_i` force zero; resolve/recovery
  clears force zero; otherwise the state holds or captures.
- The module adds no combinational path from branch resolve result back into
  fetch request PC. It only updates registered branch-spec sideband state.
