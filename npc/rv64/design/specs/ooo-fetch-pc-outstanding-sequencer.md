# OoO Fetch PC Outstanding Sequencer

## Stage 1 - Requirements

- `OooFetchPcOutstandingSequencer` owns the registered frontend fetch PC state:
  `next_fetch_pc`, `outstanding_valid`, `outstanding_pc`, and
  `discard_fetch_rsp`.
- The parent still owns fetch request selection, fetch FIFO storage, packet
  decode, branch/pending predicate generation, CSR/trap side effects, commit
  state, BPU/RAS/BTB tables, and backend drain policy.
- Inputs are single-cycle event predicates and PC payloads generated by
  `OooAluFetchCore`. Outputs are registered state consumed by the existing
  frontend run/action/request helpers and debug outputs.
- `rst` resets `next_fetch_pc` to `reset_pc_i` and clears outstanding/discard.
  A precise CSR trap is a late priority clear and redirects `next_fetch_pc` to
  `csr_trap_target_i`.
- Out of scope: changing branch prediction policy, adding extra fetch credits,
  changing FIFO seed/clear behavior, or moving pending/trap/commit state.

## Stage 2a - Protocol Rules

- The module is a fixed-latency synchronous state owner. It has no backpressure
  and no valid/ready output handshake.
- A normal fetch request arms one outstanding fetch for `fetch_req_pc_i`; a
  response without a same-cycle request clears the outstanding bit.
- A response that is enqueued or bypass-consumed advances `next_fetch_pc` to the
  packet next PC when no new fetch request fires. A new fetch request advances
  `next_fetch_pc` to the request PC.
- Redirect/recovery events overwrite the normal fetch progress in the same
  clock edge. The priority intentionally follows the old parent nonblocking
  assignment order:
  normal progress -> direct frontend flush -> branch-spec restore ->
  pending branch commit/match -> untracked branch recovery -> pending jump ->
  pending system CSR commit -> drained pending owner -> late CSR trap.
- `discard_fetch_rsp` records that an old outstanding response must be dropped
  when a redirect/trap invalidates the in-flight request. It clears when that
  stale response fires.
- Branch/JALR prefetch pending-match events can adopt the prefetch request as
  the new outstanding fetch instead of discarding it.

## Stage 2b - State Machine

| State | Encoding | Meaning | Exit |
| --- | --- | --- | --- |
| `IDLE` | `outstanding_valid=0, discard=0` | No in-flight fetch response is expected. | `fetch_req_fire_i` enters `WAIT_RSP`; redirect may set a new PC. |
| `WAIT_RSP` | `outstanding_valid=1, discard=0` | One fetch request is in flight and its response is still useful. | Useful `fetch_rsp_fire_i` without a new request returns to `IDLE`; redirect/trap may enter `DROP_STALE`. |
| `DROP_STALE` | `discard=1` | A stale response is expected and must be ignored by upstream gates. | `fetch_rsp_fire_i` clears discard; a new redirect may keep or replace the state. |

`WAIT_RSP` and `DROP_STALE` can overlap when a redirected cycle also adopts a
new request/prefetch as outstanding while an older response is still stale.

## Stage 2c - Invariants

- There is at most one architectural fetch outstanding credit:
  `outstanding_valid_o` is a single bit and is only armed by fetch request or
  prefetch-adopt events.
- `outstanding_pc_o` is meaningful only when `outstanding_valid_o` is high;
  all redirect clear paths drive it to zero when no new outstanding is adopted.
- `discard_fetch_rsp_o` can only be set by redirect/trap/recovery events that
  invalidate either an old outstanding request or a same-cycle JALR hit/request
  overlap.
- A precise CSR trap wins over every lower-priority PC/outstanding update in
  the same cycle.
- Misaligned control transfers never arm a new outstanding entry from
  `fetch_req_fire_i`; the parent trap logic owns the architectural exception.
- The module never writes fetch FIFO storage, pending payloads, CSR/trap
  registers, BPU/RAS/BTB state, or commit outputs.

## Stage 2d - Datapath Constraints

- Registers: `next_fetch_pc_q`, `outstanding_valid_q`, `outstanding_pc_q`,
  `discard_fetch_rsp_q`.
- Normal progress mux:
  - `fetch_rsp_enqueue_i || fetch_rsp_bypass_consumed_i` selects
    `fetch_rsp_packet_next_pc_i` when no request fires.
  - `fetch_req_fire_i` selects `fetch_req_pc_i` and arms outstanding.
- Direct flush mux selects JAL target, return target, branch target-cache hit,
  fallthrough append PC, branch resolve PC, branch-spec predicted PC, or branch
  fallthrough PC. Same-cycle fallthrough response capture overrides the branch
  next PC with `fetch_rsp_packet_next_pc_i`.
- Recovery muxes select CSR trap target, branch resolve target, pending branch
  target, JALR prefetch hit packet next PC, pending JALR/JAL target, MRET target,
  pending memory next PC, or pending FP next PC.
- All muxes are registered at the module clock edge; the module adds no new
  combinational path from a response or branch resolve back into fetch request
  generation beyond the existing registered outputs.
