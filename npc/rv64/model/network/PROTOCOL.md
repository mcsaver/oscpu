# CPU 事务网络：协议草案与首个实现范围

状态：2026-09-17 已实现首个协议网络原型：共同状态转移、C++/Verilog 生成、
独立参考、逐周期验证和速度测试。运行说明见 [README.md](README.md)。
整核详细执行底座现已实现，见 [CPU.md](CPU.md)；它保留原 RTL 的全部状态和 I/O，
尚未将生产模块迁移成下述高层事务原语。队列原型结果与整核验证分别记录，
生产 RTL 尚未修改。

目标是用统一的通信与节点执行语义构建 CPU：网络描述驱动软件模拟与 RTL 实现，
让队列、竞争、反压、依赖和取消成为可计算的网络行为。所有跨模块数据和控制交互
必须属于协议；时钟与复位属于显式执行环境。内部纯组合算术不要求消息化。

## 1. 验收对象

- 最终要求保持不变：相同镜像、输入、初始化、配置和统计区间下，
  模型与对应真实 RTL 的每条退休指令及其绝对周期、终止周期一致，误差为零。
- 原型验收：相同目标周期输入下，每条通道的 valid、ready、控制输出和有效 payload
  一致；输入接受、输出接受和取消事件逐周期一致。无效且无消费者使用的 payload 不比较。
- 原型尚无完整 CPU，不能用原型通过宣称整核 CPI 一致。
- 首次生产迁移以当前 RTL 为行为基线。纯结构迁移要求旧 RTL、新 RTL、模型三方周期一致。
  若选择的协议实现必须改变仲裁、缓冲或流水边界，应明确记为微架构候选，报告相对
  旧 RTL 的变化，并验证模型对新 RTL 精确；不得悄悄更换基线消除误差。
- 速度验收使用相同网络、激励、周期范围和日志设置；分别报告构建、初始化、执行时间。
  最终整核还需同镜像端到端比较，不能将已采集轨迹的计时与全功能 RTL 长跑直接相除。

## 2. 协议语言的边界

统一语义，允许不同类型、宽度和物理连接；不要求全核共享一条总线或所有消息
携带相同大包头。固定连接的路由、来源等字段可以静态确定，无需成为硬件位。

| 协议类别 | 语义 | 原型范围 |
| --- | --- | --- |
| 有界事务通道 | 有效消息、接受、保持、容量与顺序 | 实现 |
| 取消控制 | 在明确目标周期撤销指定可取消事务 | 实现 |
| 服务请求/响应 | 关联请求与完成，明确在飞容量和服务状态 | 后续执行节点 |
| 需求提示/端口预约 | 允许提前宣布需求，提示本身不产生事务接受 | 首次 WB 迁移必须实现 |
| 资源查询/原子分配 | 只读容量查询；一次动作同时取得多个资源 | 后续 Rename/ROB/IQ/LSQ 分配 |
| 发布/依赖合流 | 广播就绪、等待关联依赖，明确订阅状态与交付周期 | 后续唤醒网络 |
| 提交授权/有副作用事务 | 区分可撤销准备、不可撤销发出、完成及提交 | 后续 LSU/Commit |

后续类别是必要设计范围，目前没有声称它们已被统一的 ready/valid 自动覆盖。
不能将原子多资源分配拆为各节点独立抢占后等待，从而引入部分分配和资源死锁。

## 3. 原型的明确语义

### 3.1 身份与消息

完成消息由 owner 和 result 组成。owner 逻辑上包含 domain、slot、generation；
result 为强类型 payload。原型使用小的固定字段宽度，生产映射保留完整 ROB tag
以及结果所需字段。循环复用标识前必须确认旧事务已全部交付、取消或排空；
扩大 generation 位宽不能替代此规则。

模拟器的周期、路径、等待原因属于观察数据，除非节点功能需要，不进入硬件消息。
原型每笔输入只产生一笔终端输出，不包含广播复制。

### 3.2 周期

统一使用单时钟离散周期：

1. S[t] 表示上一个有效边沿后保存的状态，驱动本周期输入与取消集合。
2. 按显式组合依赖计算本周期输出、选择和握手，所有状态读取 S[t]。
3. 同时计算并提交 S[t+1]；随后输出供下一目标周期消费。

普通新入队消息在下一周期可见。零周期旁路必须由单独的通道实现类型声明，
不能因软件函数先后调用而自动产生。组合依赖需能调度；无寄存边界的依赖环报错。
带状态的网络反馈合法。宿主执行顺序、线程进度不能改变目标周期。

### 3.3 有界通道

通道提供 valid、ready、owner、payload。实际传输发生于对应边沿的 valid && ready。
原型外部 src_offer 是原始意图；通道 valid 已包含复位和取消匹配的限定。
未被取消的消息在等待期间保持有效及 owner/payload；发送方不以 ready 为条件
临时创造 valid。消费者只在接受事件上取得消息。

原型使用“旧占用信用、无旁路”的队列类型：本周期可接收空间由 S[t] 决定，
满队列不会因为本周期出队或取消而提前接收新消息；释放空间下一周期可见。
未来支持同拍回收或旁路时，必须声明另一种精确实现类型，并提供相应 RTL 与模型。
这些都是协议的合法实现选择，不能当作不影响周期的编码细节。

### 3.4 取消与复位

原型只处理可取消的计算结果。取消控制是具有明确有效周期的专用控制输入，
不会排在被堵塞的数据 FIFO 后面。第一版以 1..4 个完整 owner 取消端口表达本拍集合；
年龄范围、分支域、bitmap 等生产编码由后续控制节点实现同一明确语义。

本周期匹配取消的消息不产生数据接受事件；已排队匹配项在边沿删除，
保留其他项的顺序。取消释放的空间按旧占用信用规则在下一周期可用。
同步复位清空原型，复位周期不发生接受；统计按复位区间分开。
复位优先于取消，取消优先于可撤销消息交付。

不可撤销的总线请求、已授权 store 等不使用这个“删除即可”的原型规则。
扩展时必须增加排空及提交授权语义，并将未完成 owner 留在网络状态中。

### 3.5 仲裁

原型使用 3 输入、2 输出的带保持仲裁节点：

- 两个输出分别拥有一个保持槽，下游独立反压；已占用输出保持原消息和 lane。
- 可使用的输出槽由旧状态确定，低编号空槽优先。
- 从轮转指针开始按环形顺序选择有有效消息的不同输入，最多选择两个。
- 只从实际取得输出槽的输入消费消息；在边沿写入输出保持槽。
- 指针在有输入被接受时推进到最后一个被接受输入之后，无接受时保持。
- 同拍取消先屏蔽消息；取消和排空不会让旧状态已满的输出槽提前恢复信用。

这是用于验证协议/原语的确定策略，不宣称等同于生产 R64Writeback 的注册端口
grant 和需求提示策略。首次生产迁移需要对应的 RegisteredGrant 节点实现，
不能用此仲裁器直接替换并声称保持旧周期。

## 4. 第一个可运行网络

连接：3 个源 → 每源 2 项有界队列 → 上述 3×2 仲裁节点 → 2 个独立接收端。
取消控制覆盖所有排队/保持的可取消 owner。

选择该网络是为了同时覆盖不同到达节奏、满队列、输出不对称反压、竞争公平性、
固定输出保持、同拍收发、取消与标识复用。源/接收端为测试环境，按目标周期
输入和本端已观察握手行动；不使用已录好的 RTL 输出驱动软件结果。

第一批实现文件如下，均已创建：

| 文件 | 责任 |
| --- | --- |
| network/semantics.py | 小型有类型状态转移表示及三个原语定义；固定宽度、无歧义更新优先级 |
| network/completion.json | 原型实例、参数、连接和实现类型；不允许自由嵌入 C++/SV 代码 |
| network/emit.py | 将共同状态转移表示输出为 C++ 与 Verilog-2001，并检查端口类型/组合依赖 |
| network/runtime.hpp | 目标周期推进、事件采集与网络统计；不保存 RTL 测得的周期作为预测输入 |
| network/tests/ | 独立协议断言、激励与逐周期比较；同时检查两端输出与协议本身 |
| network/run.py | 构建/运行两端、生成差异与性能摘要；临时编译目录自动清理 |

只生成连接和参数不足以消除模型漂移：队列与仲裁的控制状态转移也需共用定义。
第一版固定这几个原语，不开发通用编程语言、全核自动 RTL 反推或复杂插件系统。
同源生成可能共享错误，因此独立性质检查与后续生产 RTL 对照仍不可省略。

## 5. 原型最小验收

1. 空闲、单源、三源竞争、双出口不对称反压、长时间满队列后恢复。
2. 非满同拍入/出与满队列同拍出，检查信用生效周期。
3. 等待中的 head/内部项取消、取消与发送同拍、取消与仲裁同拍、复位后重新运行。
4. owner 槽位不同 generation、取消后安全复用；旧消息不得变成新事务。
5. 定向用例及固定种子混合激励，全部通道逐周期零差异。
6. 独立检查保持、容量、单次交付、未取消消息最终排空。
   公平性检查限定为接收端持续提供容量，不声称在无限反压下保证进展。
7. 每个复位区间验证：
   接受输入数 = 终端交付数 + 已取消数 + 仍在飞数。
   中间节点转移不重复计为外部接受；复位丢弃单独归入边界统计。
8. 无详细逐周期日志的同负载计时，分别给出软件模型、RTL 仿真的时间；
   若短用例由进程启动主导，报告该限制，不宣称整核加速。

输出用 JSON/CSV：接受与服务率、队列占用、等待时间、反压持续时间、仲裁等待、
取消/排空数量，以及第一处边界差异。观察到的等待类别可以重叠，不相加伪造 CPI。

- [LSU 提示与写回组合测试](../../testbench/chengyue64/tb_r64_lsu_wb_request.sv)

迁移时必须将 demand hint、注册 grant、固定 lane、owner 查询/证书、取消及 reuse
保护纳入协议。尤其 hint 只允许影响端口预约，不能凭提示生成有效完成。
当前 LSU 输入为有序前缀接受，输出为固定 lane 独立接受，不能统一成一个未声明的多 lane 规则。
普通 store 的窄完成、分支 resolve 和短 ALU 提前唤醒各有语义，不可丢弃。

实施顺序：

1. 建立协议原语、共同状态转移定义及双端可运行原型，完成第 5 节验收。
2. 增加生产策略的节点，以协议实例重建结果回流子网；独立比较旧 RTL、新 RTL 和软件。
3. 接入真实 Backend/ROB/唤醒路径，完成相关定向、真实 DiffTest 和周期对照。
   结构改变时评价对应综合/STA 代价，不能用更易模拟替代 CPU 本身的性能。
4. 扩展到发射/执行，再到 LSU/cache 和前端；按需引入原子资源分配、
   有状态服务、发布/合流与不可撤销事务。
5. 完整 CPU 网络需要执行驱动与功能状态反馈，覆盖错误路径及时间敏感输入；
   当前 correct-path trace 模型不能直接当作完整网络的功能执行器。
6. 回到相同完整镜像的周期零误差与端到端速度验收。

上述顺序是实现依赖，不是新增用户审批、marker 或发布门槛。
当前已完成第 1 步的可运行原型与测试；第 2 步起的生产迁移、整核精度与速度
尚待实现和测量。原型运行记录由 run.py 写入指定输出目录。
