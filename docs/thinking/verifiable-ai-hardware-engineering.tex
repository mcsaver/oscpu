\vspace{0.7em}
\noindent\textbf{摘\quad 要：}
大语言模型已经能够生成寄存器传输级（Register Transfer Level，RTL）代码并调用编译、仿真、综合
和静态时序分析工具，但复杂处理器开发并不是一次自然语言到 Verilog 的映射。体系结构语义、跨模块
时序、软件工作负载、参考模型、验证判定器和物理实现条件需要在同一工程上下文中持续协同；只提供
源码和 shell，模型仍难以稳定完成由需求分析延伸到系统验证的长链任务。

本文提出 \textbf{Loop-Work}，一种面向集成电路工程的仓库原生领域 Agent 构建方法。其核心不是为
候选增加一个事后审批步骤，而是把项目知识、任务控制、工具执行和分层验证组织成 Agent 可发现、
可调用并可演进的工程环境。控制、知识、执行和证据四个责任平面规定能力由什么构成；任务内修订环
使分析、设计、实现和验证相互反馈，跨任务能力环则把反复出现且具有迁移价值的经验固化为
instruction、Skill、端到端执行剖面、测试和门禁。候选资格化只是证据平面防止错误结果进入后续节点
的一项机制。

本文采用近四个月的 ysyx-workbench 纵向案例，覆盖从 C/汇编测试程序、Abstract Machine（AM，
抽象计算机运行时与平台适配层）到 NEMU 参考机、RV32 五级流水核、ysyxSoC 接入和 RV64 双发射乱序核
的连续演进。NEMU 已形成支持 RV64 M/A/F/D/C、系统态执行及 UART、virtio-blk、PLIC 相关中断、
RTC 和关机设备的参考平台；AM 与 am-kernels 将应用构建、设备抽象和体系结构测试组织为可在参考端与
RTL 目标端复用的工作负载；NPC（本项目的 RTL 处理器目标）则由 RV32I 主通路演进为支持
RV64IMAFDC、Zicsr、Zba/Zbb/Zbc/Zbs、M/S/U、Sv39、硬件页表遍历、I/D TLB、PMP16、浮点和原子路径
的小窗口双发射乱序核。当前同一设计身份下记录了 113/113 项模块测试、177/177 项 official
riscv-tests、61/61 项 AM 测试、DiffTest 失配为 0，以及 L0 定向 RTL、L1 完整核、L2 mini-system 和
L3 轻量 Linux 四层验证通过。

案例表明，模型能力与仓库工程环境是共同构建的：Agent 不仅生成 RTL，也消费接口合同；不仅生成
测试，也利用 NEMU、AM、testbench、负向变体和系统运行反驳自己的候选；需要性能结论时，再由
Yosys、OpenSTA 和开源工艺库提供实现反馈。当前架构已形成 \statusword{ARCH\_STABLE} 收据，PPA
仍保持 \statusword{UNQUALIFIED}。本文据此报告方法如何被实例化及其已经形成的工程产物，但不把
单仓库观察外推为相对于其他 Agent 方法的因果优势，也不以预布局代理结果替代物理签核。

\section{引言}

\subsection{问题背景与研究动机}

在最初建立 RV32I 取指、译码、执行、访存和写回主通路，并把 AM 生成的裸机镜像装入处理器仿真时，
Agent 已能较快补充译码、算术逻辑和局部控制代码。此时目标集中在基础整数指令和单发射五级流水，
工程师可以直接指出源文件、运行命令和 GOOD TRAP 条件；即使一次生成遗漏 testbench、存储模型或
退出协议，也能够在较短的人工反馈路径内补齐。

任务随后由单核裸机运行扩展到 ysyxSoC 地址空间与 AXI 接口，再扩展到 RV64、浮点与原子指令、
M/S/U 特权级、Sv39 地址转换、双发射乱序执行、OpenSBI/Linux 以及 CPI/PPA 分析。此时一次 RTL 修改
可能同时改变请求 owner、反压传播、flush 与精确异常顺序，并要求 NEMU 参考语义、AM 测试程序、NPC
提交状态和综合约束同步更新。代码即使能够编译，也可能因为遗漏架构前提、选择错误后端、使用过期
日志或由过弱判定器给出绿色结果而无法进入后续开发。

这些连续任务揭示的瓶颈不再只是“生成速度不够”，而是领域知识怎样被送入当前上下文、自然语言目标
怎样先被分析并转成受权任务、设计与测试怎样共同产生、NEMU/AM/NPC/EDA 的观测怎样互相校验，以及
本轮反例怎样在下一轮不被遗忘。延长单个提示或增加一次人工审查能够缓解局部问题，却不能稳定保存
仓库关系、工具入口和验收层级；会话或模型变化后，相同的工程事实仍可能被重新发现和重新踩坑。

本文据此把研究对象从“如何让模型生成一段 RTL”推进为“如何在集成电路工程中构建一个能够工作的
领域 Agent”。本文提出 Loop-Work，把控制、知识、执行和证据组织为四个责任平面：前两者使 Agent
在写代码前理解目标、边界和专业约束，后两者使其能够生成并消费 RTL、测试、反例与工具反馈。任务内
闭环用于完成当前修改，跨任务闭环把稳定经验固化为 instruction、Skill、E2E、测试和门禁。候选是否
可由下游消费由证据面判定，但它只是整套领域能力中的一环，而非方法的全部。

在 ysyx-workbench 中，NEMU、AM 和 NPC 不是三个并列项目：AM 产生可复用程序镜像，NEMU 提供指令级
参考状态，NPC 是被开发的 RTL 目标，DiffTest 在退休边界比较二者；模块 testbench、L0--L3 系统验证
以及 Yosys/OpenSTA/开源 PDK 又分别增加周期级、系统级和实现级反馈。本文将以这条真实数据流说明
Loop-Work 如何落地，并以 NEMU、AM 与 NPC 的纵向产物检验 Agent 工程能力扩展到了何种范围。

\subsection{研究问题}

全文围绕五个研究问题展开：

\begin{enumerate}
  \item \textbf{RQ1（领域能力构成）：}怎样把分散在设计规范、源码、脚本、工具和历史记录中的
  集成电路知识，组织为 Agent 可发现、可调用并可维护的仓库原生环境？
  \item \textbf{RQ2（目标到任务）：}怎样把工程师的自然语言目标转换为“先分析、后实施”的任务图，
  使 Agent 能够确定设计边界、选择规则和工具、分配责任并控制修改范围？
  \item \textbf{RQ3（设计---验证闭环）：}Agent 怎样在 AM、NEMU、NPC 和 EDA 工具之间生成并消费
  架构方案、RTL、测试程序、反例和执行证据，并在设计增删后保持跨层一致性？
  \item \textbf{RQ4（能力演进）：}编译失败、仿真反例、差分失配、系统缺口和 PPA 反馈怎样被固化为
  instruction、Skill、E2E、测试和门禁，从而扩大后续任务可独立闭合的范围？
  \item \textbf{RQ5（工程产物与边界）：}Loop-Work 在 ysyx-workbench 的 NEMU、AM 和 NPC 上形成了
  哪些工程产物，跨越了哪些验证压力层级，现有证据能够支持和不能支持哪些结论？
\end{enumerate}

\subsection{主要贡献与研究范围}

本文围绕上述问题给出五项贡献：

\begin{enumerate}
  \item 提出一种面向集成电路工程的领域 Agent 构建观点：Agent 的有效能力由基础模型与仓库原生
  工程环境共同构成，而不能只用一次代码生成质量衡量。
  \item 将领域 Agent 形式化为控制、知识、执行和证据四个责任平面，并给出任务内修订与跨任务能力
  固化两类反馈边，解释能力如何运行及如何增长。
  \item 给出从工程目标、写前分析、接口合同和 RTL 拓扑，到 TB、负向变体、AM 程序、DiffTest、
  L0--L3 系统验证与 EDA 反馈的完整任务方法，使设计与验证成为同一任务的共同产物。
  \item 给出由 instruction、Skill、机器合同、E2E profile、受控执行和证据收据组成的仓库级参考实现；
  身份拒绝、负向资格、长跑失败关闭和有界晋级作为其中的四项运行约束接受反例检验。
  \item 给出 RV32 single、ysyxSoC、NEMU/AM/NPC、RV64 双发射 OoO、分层 Linux 和 CPI/PPA 的纵向
  工程结果，并用机器可读主张、同身份回归和独立反例复核限定结论边界。
\end{enumerate}

研究材料来自一个持续演化的仓库，本文据此讨论方法接口的可执行性、可审计性及其在所列 RV64 压力
层级上的实例化，不把纵向共现解释为生产率因果效应。全文依次讨论相关工作、问题与设计要求、方法与
参考实现、案例研究设计、纵向工程证据、命题与成果综合、未闭合目标及结论。

\section{相关工作与方法空缺}

\subsection{Agent、RTL 生成与 EDA 自动化}

SWE-agent 说明 Agent--Computer Interface 会影响仓库级软件任务的执行方式
\cite{yang2024sweagent}；VerilogEval 用 testbench 通过率评价 Verilog 生成
\cite{liu2023verilogeval}；ChatEDA 研究大模型对 EDA 工具链的规划与执行\cite{wu2024chateda}。
MAGE 进一步用多 Agent 候选采样、调试和 Verilog 状态检查提高模块级生成结果
\cite{zhao2025mage}。近期一项 CVDP 实验显示：对多数受测模型，直接套用基线工具 Agent 的 Pass@1
低于相应的无工具单次基线；加入结构化系统提示后，差距缩小，部分配置持平或反超
\cite{yubeaton2026agentic}。这一结论只适用于该论文的模型、任务子集与 harness，不说明 Agent 在一般
RTL 任务中更弱。NotSoTiny 进一步在结构更复杂的上下文模块补全任务上比较原生 testbench 与形式
等价：在 1114 个去重并验证的模块补全任务上，语法有效输出有 95--97\% 可通过原生 testbench，
而 11 个受测模型在形式等价下的完全正确率为 3.3--23.4\%；其中四个相对较高结果也仅为
19.0--23.4\%\cite{ghorab2025notsotiny}。其中时序设计采用
有限深度的 \texttt{equiv\_induct}（$k=30$），因而这一范围只描述其数据集、模型和验证协议，却直接
提醒读者：正向
testbench 接受率不能替代独立的语义资格。

ACE-RTL 以 generator、reflector 和 coordinator 维护迭代调试上下文，其预印本报告在 CVDP 上相对
14 个基线最高 41.02\% 的 pass-rate 改善\cite{deng2026acertl}；NVIDIA 随后的官方技术发布又报告
Nemotron 3 Ultra 配合该 Agent 在九类 CVDP 任务上的平均 pass rate 为 97.1\%
\cite{nvidia2026acertl}。本文以前一项预印本结果作为学术论证锚点；后一个数值来自未经同行评议的
厂商技术博客，是平均通过率而非 Pass@1，只作补充背景，也不能延伸为系统级签核率。
FluxBench 在统一提示、工具和工艺库下评价 RTL 生成与 RTL-to-GDS 流程，报告同一基础模型的 Agent
系统在固定 DeepSeek-V4 与 350\,MHz 条件下的 0--100 端到端得分为 11.67 至 97.94，即相差
86.27 个\textbf{绝对分值点}；这不是 86.27\% 的相对提升。其当前 v3 在 PicoRV32、55\,nm、
350\,MHz、各配置仅运行一次的实验中，还给出两项端到端得分同为 13.33、但归一化 Token ROI 为
12.71 与 0.09 的 Agent 配置，二者相差约 141.2 倍
\cite{deng2026fluxbench}；这不是纯 Token 数之比，也不能归因于单一模型或单一组件。
Design Conductor 则报告从 219 词需求出发，在 12 小时内为 RV32I+Zmmul
VerCore 形成满足 ASAP7 1.48 GHz 时序的 GDSII\cite{verkor2026designconductor}。这些结果表明，相关
系统已在各自任务与评价协议下报告了迭代反馈和端到端自治能力的进展；由于设计、工具、工艺与
oracle 均不同，它们不构成本文 RV64 OoO、
Ubuntu 长跑或 PPA 资格的横向基线。

\subsection{仓库级修复与 Agentic 验证}

CVDP 将 RTL 生成、验证、调试和规格对齐组织为 783 个问题及 13 类任务
\cite{pinckney2025cvdp}；HWE-Bench 把真实历史硬件缺陷转化为六个开源项目中的 417 个仓库级修复
任务，并指出定位、硬件语义与 RTL/配置/验证跨产物协调是主要失败环节\cite{cui2026hwebench}。
PRO-V-R1 使用程序化工具反馈训练自主 RTL 验证 Agent\cite{zhao2025prov}；GoGoTB 则把执行控制、
可演化知识和规格绑定覆盖闭合连接起来\cite{xin2026gogotb}。这些工作已经覆盖角色分工、反馈循环、
验证环境生成和仓库任务，因此本文不以“首次使用 Agent 闭环”为贡献。本文关注的是另一条轴：同一
repository-native 生命周期中，怎样把任务权限、适用知识、真实执行和证据资格保持为可区分状态，
并让中断、旧身份、弱 oracle 和不合格 PPA 进入不同终态。

LLM4Cov 把确定性执行反馈用于离线 Agent 学习，并在 CVDP-ECov 的 Agentic evaluation 上报告：4B 模型
生成测试平台的 pass rate 为 69.2\%，平均覆盖率为 90.4\%\cite{zhang2026llm4cov}；二者都不是 RTL
功能正确率或完整验证闭合率。Si2 的 LBC-bench 则以 CVDP 为初始重点，公开 leaderboard
数据格式、提交标签和可复现入口\cite{si22026lbcbench}。前者研究怎样提高覆盖闭合候选，后者提供
公共比较基础设施；二者都可为后续对照实验提供任务或评价协议，但公开 leaderboard 本身不能充当
隐藏 oracle，也不承担本文主张的独立真值责任。

\subsection{Mutation 与硬件故障注入}

Mantra 从真实硬件缺陷构造 mutation 算子，并以 mutation score 评价测试敏感度
\cite{wu2023mantra}；基于 HDL 的故障注入研究也表明覆盖率受到故障模型、工作负载和注入技术影响
\cite{gil2003faultinjection}。Firefly 在 Maveric Core 2 与 Bitty 两个对象上报告：组合 line/toggle
coverage 分别达到 95\% 与 90\% 时，其注入 fault set 中仍分别有 28\% 与 67\% 未被检出
\cite{skakov2025firefly}。该结果不能外推到所有覆盖率或所有故障模型，但说明常规覆盖率与 fault
sensitivity 不是同一构念。BugGen 则用多 Agent 生成、插入和验证 RTL 缺陷，在五个 OpenTitan IP 上
产生 500 个唯一注入缺陷，报告 94\% functional accuracy 与每小时 17.7 个 validated bugs；其中 104 个
生成变体绕过既有回归\cite{jasper2025buggen}。这里的 104 是未被回归检出的注入变体，不是 104 个
新发现的 OpenTitan 真实缺陷。

Firefly 与 BugGen 主要解决上下文相关 fault 的生成、验证基础设施诊断或数据集扩展；本文后述的
负向资格化命题关注
这些 fault 如何成为不可绕过的晋级资格。为此，“变体可编译、语义变化非空、错误被触发、错误传播到
观察点、判定器拒绝、campaign 完整”必须同时成立。本文当前 23 个定向 mutant 与上述论文的数据集
没有共同分母；检测给定变体仍然不能证明 DUT 全局正确或 oracle 完备。

\subsection{追踪、可信论证与构建来源}

需求追踪研究关注需求来源和生命周期链接\cite{gotel1994traceability}。W3C PROV-DM 以 entity、
activity、agent 及其派生关系表达来源与责任\cite{w3c2013provdm}；GSN 和 SACM 则组织 goal/claim、
argument、context 与 evidence 的可信论证\cite{scsc2021gsn,omg2023sacm}。in-toto 与 SLSA 强调供应链
步骤、materials/products、构建来源和抗篡改控制\cite{torresarias2019intoto,slsa2025v12}。这些标准
能够承载本文的部分对象，但来源真实不等于证明力充分，论证结构完整也不等于仓库作业已经执行。
本文不发明 provenance 或 assurance-case 语法，而把它们与 task contract、工程 oracle、失败关闭状态
和晋级责任连接；这里的 oracle 是把日志、trace、计数器或波形转换为机器判定的参考模型、断言或规则，
它本身也必须被资格化。

\subsection{质量门、UVM 与工业准备度}

持续交付中的 quality gate 研究讨论发布可信度与速度的权衡\cite{schermann2016qualitygates}；
UVM 标准化验证组件和接口\cite{ieeeiec2023uvm}；ISO 26262-5 规定汽车硬件安全生命周期和工作产品
\cite{iso2018functionalhardware}。Siemens 与 NVIDIA 的 2026 年官方产业发布把长运行 Agent、
OpenShell 的 access control/audit trail 与确定性、physics-based EDA engine 的持续校验组合为
self-verifying workflow\cite{siemens2026selfverifying}。这说明工业系统也在把验证反馈和治理放入
Agent 运行时；该公开材料是产品/技术发布，没有给出可用于因果比较的同行评议实验，也未把所有
责任状态形式化为本文的类型化晋级序列。

本文不声称符合 UVM、SLSA 或 ISO 26262，也不替代物理 signoff。
本文将上述已有机制组合并约束到 repository-native 场景：把本地 module/signal/transaction、验证层级、

\section{集成电路领域 Agent 的构建问题与设计要求}
\label{sec:problem-definition}

相关工作表明，候选生成、工具反馈、来源追踪和阶段门禁已经分别取得进展，但它们尚未统一回答：
一个通用模型怎样在真实集成电路仓库中获得分析架构、受控修改、构造验证、调用工具和吸收反馈的领域
能力。本文先把这一缺口写成领域 Agent 的构建问题，再由失效模式推导方法所需的责任接口；候选验收
是其中的证据责任，而不是问题定义本身。

\subsection{处理器 Agent 任务的失效结构}

处理器开发任务不能只写成“修改某个模块”。本文把任务定义为

\[
\mathcal{T}=\langle c,O,K,U,Q,E\rangle,
\]

其中 $c$ 是待证明的工程主张，$O$ 是 RTL、软件、配置与 workload 构成的对象集合，$K$ 是必须遵守的
领域知识，$U$ 是授权动作，$Q$ 是分层验收谓词与门禁，$E$ 是必须保留的证据。开放式 Agent 往往只
接收 $c$ 的自然语言近似和部分 $O$，因而在对象、动作和完成条件上留下歧义。任务还必须绑定实现责任
与独立复核责任；具体角色接口在控制面小节统一定义。表\ref{tab:failure-requirements}从实际工程压力
推导出方法要求。

这些失效并不是六个彼此独立的脚本问题，而是“Agent 能力如何被构成”的四类责任缺口：目标和权限
没有被控制；规则虽存在却没有被选择到当前任务；模型不能在确定环境中把方案转化为真实工程动作；
工具虽产生观测，却没有形成可反驳、可复用的验证结论。若只增加提示长度或工具数量，知识、动作和
验证仍可能彼此脱节；若再把四类状态压成一个 GREEN，身份漂移、弱判定器和不完整长跑便成为不可
表达状态。

\subsection{由失效模式推导的设计原则}

上述四类责任缺口导出六项设计原则：

\begin{enumerate}
  \item \textbf{合同先于生成：}先定义对象、输入、输出和成功条件，再允许 Agent 修改或运行。
  \item \textbf{身份先于比较：}baseline 与 candidate 身份不一致时，不计算正式改善。
  \item \textbf{原始观测不可改写：}新 checker 可以生成新解释，但不能覆盖原始 FAIL/PASS。
  \item \textbf{正向与负向证据并存：}当前版本 PASS 还要接受能够暴露目标错误的反例检查。
  \item \textbf{局部接受与工程晋级分离：}focused、module、system、PPA 分别承担不同结论。
  \item \textbf{高成本验证受决策约束：}长跑必须能够改变明确决策，并在开始前完成低成本排除。
\end{enumerate}

这些原则共同要求一种带类型的闭环：控制责任把目标变成可执行任务，知识责任提供适用规则，执行责任
同时产生设计、测试和原始观测，证据责任用正反例决定观测能够支持什么结论。增加模型参数或工具数量
只能扩大潜在动作集合；只有四类责任能够独立检查又共同运行，潜在能力才会转化为稳定的工程能力。

\section{Loop-Work 顶层方法}
\label{sec:method-overview}

\subsection{中心论点：模型与仓库环境共同构成领域能力}

因此，本文的核心问题是：\textbf{怎样在集成电路工程中构建一个能够工作的领域 Agent}。本文所称
Agent，是能够读取仓库材料、调用工具并根据运行结果继续行动的大语言模型执行单元；Workflow 是带
输入、输出、权限、成功条件、失败分流和证据责任的可执行任务图；Loop-Work（闭环工作轮）则把专业
知识、工程执行和分层验证组织为这种 Agent 的外部能力结构，而不是一个更长的提示词。

本文的中心论点是：\textbf{集成电路领域 Agent 的工程能力并非基础模型固有的代码生成能力，而是
模型与仓库原生工程环境共同构建的系统能力；只有把项目知识、任务控制、工具执行和分层验证组织为
可循环演进的工作流，并把任务反馈持续固化为可复用约束，Agent 才能稳定承担从架构分析、RTL 实现
到功能验证、综合和系统运行的长链任务。}四平面说明能力由什么构成，双闭环说明能力如何运行和增长；
候选验收、身份绑定与失败关闭则是证据面保护后续工程节点的具体机制。

\subsection{抽象顶层：四类责任状态与两条反馈边}

Loop-Work 的根输入是工程目标 $G$、当前状态 $S$、约束边界 $\Gamma$ 与验收准则 $A$。控制面把根输入
编译为合同、权限、owner、门禁和终止条件；知识面返回当前节点适用的规则、事实和程序化能力；执行面
在授权范围内产生候选与原始观测；证据面绑定实验身份、判定器和证据资格；控制面最后作出接受、返工、
保持缺口或终止的裁决。其责任状态与裁决写为

\[
s=\langle C,K,X,V\rangle,\qquad
d(s)\in\{\mathrm{PASS},\mathrm{FAIL},\mathrm{GAP},\mathrm{UNQUALIFIED},\mathrm{BLOCKED}\}.
\]

这里的 $C$ 是控制责任，$K$ 是知识适用性，$X$ 是实际候选与运行状态，$V$ 是身份绑定、oracle 与证据
资格。图\ref{fig:double-loop}给出全文唯一的动态总览：$C_{\mathrm{prepare}}$ 和
$C_{\mathrm{decide}}$ 是同一控制面的准备端与裁决端，$K/X/V$ 分别对应另外三个平面。内层闭环把当前
任务的反例和证据缺口送回当前合同，外层闭环只把重复且可迁移的缺口送回可复用能力。\textbf{双闭环
是四平面主干上的两类反馈边，不是第五和第六个平面。}

使用；它服务于领域 Agent 的构建，而不是取代前面的分析、设计和验证活动。

因此，本文的必要性主张是“状态类型不可无损省略”，而不是“必须建立四套工具”。ACI、quality gate、
W3C PROV、GSN/SACM 可以分别实现这些接口的一部分；若一个实现把它们合并到同一数据库或程序，但仍
保留四类字段、版本和裁决边界，则只是物理封装发生变化，并没有消除这四类责任。反之，若合并结果
只剩一行无类型 GREEN，表\ref{tab:plane-minimal-counterexamples}中的状态对将不可表达。

这一分解也不与最新 Agent 架构或产业 self-verifying stack 争夺同一层次。ACE-RTL 的 generator、
reflector、coordinator 是候选生成和调试上下文的角色分解\cite{deng2026acertl}；Siemens 公开材料列出的
确定性 EDA engine、NeMo Gym、OpenShell、Nemotron/Switchyard 与 GPU 加速是技术栈构件
\cite{siemens2026selfverifying}。前者可承载 $K/X$ 的迭代，后者可分别承载执行、治理和判定接口，
但这些物理构件怎样部署并不自动决定裁决状态怎样编码。就公开材料而言，它们没有报告与本文相同的
design/build/workload/oracle/evidence 强身份元组、mutation 资格和成熟度全序；这里应理解为“未报告
同一形式化接口”，而不是断言其系统不存在等价内部机制。反过来，Loop-Work 的四面也不替代专用模型、
物理引擎或安全运行时；它只规定这些构件的输出在成为下游结论前必须保留哪些可区分责任状态。

本文的贡献定位于责任状态的显式形式化，而非新增底层工具能力：权限、知识适用性、真实执行和证据资格在
既有系统中可能由不同工具隐式承担，Loop-Work 的增量是把它们编码为可版本化、可审计且可证伪的
责任状态。若这些状态未被类型化，表\ref{tab:plane-minimal-counterexamples}中“观测相同而正确裁决
不同”的状态对便无法区分，责任归属、旧证据失效和失败关闭消费也无法由第三方复核；显式形式化则
为 P1--P4 提供了可检查的接口。该收益来自可表达性与可审计性，而不是对既有工具能力的优先权声明。

目标进入体系后，首先必须确定它属于哪类工程活动、允许改变什么以及在何种条件下结束，因此先从控制面
展开这棵树。

\subsection{控制面：从根目标到权限化任务图}

控制面回答四个问题：本轮究竟要证明什么，谁拥有当前节点，允许改变哪些对象，以及哪些结果能够终止
节点。它先把自然语言请求归一化为任务类别，再把类别映射为权限、证据义务、收尾门禁与留存档位。
因此，分类不是给任务贴标签，而是一个全定义路由函数

\[
\mathcal{R}(\tau)=\langle W_{\tau},E_{\tau},Q_{\tau},L_{\tau}\rangle,
\]

其中 $\tau$ 为任务类别，$W_{\tau}$ 为写入权限，$E_{\tau}$ 为最低证据义务，$Q_{\tau}$ 为终止时
允许或必须执行的门禁，$L_{\tau}$ 为
task-run 留存级别。每一种类别都必须得到四个值；“零门禁”和“禁止写入”也是明确的路由结果，
并非该类别没有经过控制面。

不能沿用旧类别的权限继续执行。

\subsubsection{“大目标”与图节点的关系}

本文所称大目标并非原始对话全文，而是归一化后的复合验收目标

\[
G=\langle\text{claim},\text{objects},\text{hard constraints},\text{acceptance}\rangle .
\]

例如，一次 RV64 性能基线复核的大目标是：在同一设计、配置和 workload 身份下，核算双发射计数器
端点与 cycle/slot 守恒，检查多次运行和统计开关的非干扰性，保留 A1（第一次原始性能基线执行）和
A2（同一冻结配置下的第二次独立执行）的原始 FAIL，并在物理
条件不足时维持 PPA 为 \statusword{UNQUALIFIED}。该目标同时包含多个可独立失败的义务，不能交给
一个“查看全部然后判断”的超大节点。控制面因此把它拆成依赖图：身份冻结、计数器核算、重复性检查、
失败状态复核、独立反例审查和聚合裁决分别成为节点。

图节点不是一段伪代码，而是一个具有输入端口、授权边界和输出端口的合同，如图
\ref{fig:node-contract}所示。上游只能提供合同列出的输入；节点内部动作受 owner 与权限包络约束；下游
只能消费已经声明的产物和证据。缺少 evidence 的节点不能成为下游硬依赖。

\subsubsection{调度器、实现者、审查者与 oracle}

在前述任务定义与设计要求的基础上，控制面进一步固定以下四类角色及其接口：

\begin{enumerate}[label=\arabic*.,leftmargin=2.2em,itemsep=0.25em,topsep=0.35em]
  \item \textbf{调度器：}维护节点依赖、读写权限、owner 分配与状态迁移；它决定哪个节点可以开始，
  但不替代节点内的专业判断。
  \item \textbf{实现者：}在合同授权范围内生成候选，并运行合同指定的定向验证；它提交候选和原始
  观测，无权用自己的总结宣布独立审查通过。
  \item \textbf{审查者：}作为独立只读节点，不继承实现者的结论，依据同一验收谓词寻找反例、转录
  错误和越级声明；其 PASS 只覆盖合同列出的材料，不能替代未运行的 testbench、综合或 STA。
  \item \textbf{判定基准（oracle）：}由参考模型、断言、checker 或形式化谓词提供机器可判定的比较
  标准。它是验收接口而不是人格角色，也不能在输入身份不一致时给出有效裁决。
\end{enumerate}

控制面至此给出了问题、权限、角色和终止条件，但它本身不提供 RTL 事实、专业规则与历史经验；这些
输入由知识面按当前节点构造。

\subsection{知识面：从开放仓库到有界上下文包}

知识面回答“当前节点需要知道什么、这些内容从何而来、哪些结论允许复用”。其输出不是文件名列表，
而是带来源的有界上下文包

\[
B_i=\langle R_i,F_i,H_i,P_i,\Pi_i\rangle,
\]

其中 $R_i$ 是不可违反的规则，$F_i$ 是当前源码、spec、testbench、配置和工具事实，$H_i$ 是按当前
profile 与主题检出的历史证据，$P_i$ 是可调用的 Skill、E2E 与 oracle，$\Pi_i$ 是每一项内容的路径、
版本或哈希来源。控制面以节点合同为查询条件，知识面只返回完成节点所需的最小充分集合；全量聊天、
无关日志和过期快照不进入 $B_i$。

  \centering
  \small
  \caption{知识面的层级、输出语义及其边界}
  \label{tab:knowledge-plane-layers}
  \begin{tabularx}{\linewidth}{@{}L{0.20\linewidth}L{0.27\linewidth}L{0.27\linewidth}Y@{}}
    \toprule
    知识层级 & 回答的问题 & 进入节点的形式 & 单独不能证明什么 \\
    \midrule
    全局 policy/AGENTS & 所有任务都不能越过哪些行为边界 & 任务分类、语言、记录和安全约束 & 不能替代模块 spec 或业务测试 \\
    作用域 instruction/spec & 当前模块、接口或 PPA 路径必须保持什么不变量 & 硬约束、验证顺序、接口谓词与晋级条件 & 文件存在不等于不变量已被执行 \\

这里需要区分 instruction、Skill 和 E2E。instruction 是声明式规则，规定“什么不能错”；Skill 不是
知识本身，而是把已经选定的专业规则编译为可重复执行的步骤、合同和产物模板；E2E 也不是“完成知识”，
而是把规则、Skill、执行入口、观测点和终止条件组织为可执行闭包，并检查这些对象之间的接线与证据链。
控制面依据任务类别与路径选择三者，执行面调用其中的操作，证据面消费其中的验收谓词。因而
Skill/E2E 虽以文件实现，却不是与四面平行的第五层：它们首先属于知识面，只有被控制面选择后才在
执行面运行，并由证据面裁决。

以本地 RV64 子任务为例，\taskpath{rtl-agent-task-contract.instructions.md} 没有保存某次对话答案，
而是把“审查一段 RTL”拆为工程域、任务类型、可读路径、可写路径、规范命令、必读 RTL/spec/TB、
交付物和成功条件。相应 Skill 将这些字段编译为带版本与 SHA-256 的 JSON 合同；E2E 再检查 instruction、
Skill、合同生成器、执行节点与证据入口是否接通。这样，一条接口经验才从供模型阅读的文字，转化为
能够限制写入、拒绝越界命令并接受反例检验的工程能力；合同检查通过仍只证明任务边界清楚，不能替代
该 RTL 的 testbench、DiffTest、综合、静态时序或 PPA 判定。

知识面还承担外部知识进入工程的净化边界。一次 task-run 的原始日志只进入证据索引；被反复验证且
跨任务稳定的结论才进入 retained memory；需要持续约束动作的结论进入 instruction；可重复操作进入
Skill；需要自动组合和验收的能力才进入 E2E。这样，工作区不会把“发生过”误写成“以后都成立”，
也不会把所有历史过程重新灌入模型。

有界上下文包把开放工程目录压缩为当前节点能够消费的确定输入，执行面据此产生候选和原始观测。

\subsection{执行面：在合同授权内产生候选与原始观测}

执行面只回答“实际做了什么”。它接收节点合同和有界上下文包，调用主 Agent、子 Agent、编译器、
仿真器、DiffTest、综合、STA 或系统回放，输出三类对象：候选变更 $\Delta_i$、原始观测 $O_i$ 和
运行状态 $\sigma_i$。执行面无权把三者自行解释为 PASS；即使命令返回 0，身份、日志完整性、oracle
和清理状态仍需交给证据面资格化。

单个节点只有一个对外 owner。实现者、验证者和只读审查者可以是节点图中的不同 owner，但不能同时
争用同一工作区写权限或同一工程 shell。对于本地 RV64 RTL，机器合同进一步冻结
\texttt{allowed\_paths}、\texttt{write\_paths}、结构化
\texttt{command/mode/purpose}、必读上下文、交付物与成功条件。子 Agent 以隔离上下文执行；所需
设计事实由合同显式提供，而非依赖父会话中未登记的叙事。

图\ref{fig:rtl-contract-dispatch}给出本地 RV64 节点从父图到证据提交的执行路径。只有合同创建、结构
校验和渲染绑定均通过，owner 才得到执行权；若发现范围不足，当前节点返回
\texttt{scope\_extension\_request}，由控制面创建新版本合同并重新经过校验，旧合同不会被口头扩大。

短命令与小时级作业共享同一合同接口，但状态保存不同。短命令可以直接回传返回码和 bounded log；长时间
仿真、综合、STA 或系统回放还必须持续记录 stage、signal、evidence-complete 与 cleanup，防止交互终止
或进程退出被误当作工程完成。这些状态仍只是执行事实，下一节才定义它们怎样成为可接受证据。

\subsection{证据面：从原始观测到限定结论}

证据面回答“哪些执行结果可以被相信，以及只能在什么范围内被相信”。它将执行面的
$\Delta_i,O_i,\sigma_i$ 与设计、配置、工具、workload、oracle 身份 $I_i$ 绑定，再按验收谓词
$Q_i$ 资格化：

\[
\mathcal{A}_i=\operatorname{qualify}(\Delta_i,O_i,\sigma_i,I_i,Q_i).
\]

资格化至少检查对象一致性、原始日志完整性、预期终端 marker、正反例判定、返回码、信号与清理状态。
独立审查报告可以成为 $O_i$ 的一个输入，但审查文字不能覆盖 raw log，也不能把合同外对象纳入结论。

\begin{table}[htbp]
  \centering
  \small
  \caption{证据面的状态及其可消费边界}
  \label{tab:evidence-status-semantics}
  \begin{tabularx}{\linewidth}{@{}L{0.18\linewidth}L{0.35\linewidth}Y@{}}
    \toprule
    状态 & 形成条件 & 下游允许的动作 \\
    \midrule
    PASS & 本节点的身份、运行、证据、oracle 与清理全部满足合同 & 仅在该节点声明范围内作为硬依赖 \\
    FAIL & 已观察到合同内反例、命令失败或中断状态 & 定位、回滚或生成下一实验；保留原始失败 \\
    GAP & 输入、身份、观察点或覆盖不足，无法作出真假判定 & 请求补证或扩展合同；不得自动当作 PASS \\
    UNQUALIFIED & 作业完成，但量测或物理条件不足以支撑性能/PPA 结论 & 仅保留诊断价值，不允许晋级或 Pareto 比较 \\
    BLOCKED & 上游合同、上下文、发布或基础设施前提未闭合 & 停止下游消费，先修复阻塞对象 \\
    \bottomrule
  \end{tabularx}
\end{table}

对于长时间作业，最小 PASS 条件为

\[
\mathrm{PASS}=C_{\mathrm{run}}\land C_{\mathrm{evidence}}
\land C_{\mathrm{cleanup}}\land\neg C_{\mathrm{signal}}.
\]

所以“进程退出 0”只满足 $C_{\mathrm{run}}$，并不等于工程成功。证据不完整、清理失败或收到
HUP/INT/TERM 时，状态必须失败关闭。原始 FAIL 可以由修订后的 oracle 在冻结输入上产生一个新的
replay 结论，但旧状态不得被追溯改写。

本文最终把第 $k$ 轮有效交付定义为

\[
\mathcal{D}_k=\langle\Delta_k,\mathcal{E}_k,\mathcal{P}_k,\mathcal{V}_k\rangle,
\]

其中 $\Delta_k$ 是工程变更，$\mathcal{E}_k$ 是正向与负向证据，$\mathcal{P}_k$ 是设计、构建、
workload、oracle 与原始产物的来源绑定，$\mathcal{V}_k$ 是限定判定。任何一项缺失，产物只能保持
候选、GAP 或 UNQUALIFIED；若缺失源于上游合同、上下文、发布或基础设施前提未闭合，则状态为
\statusword{BLOCKED}。这些状态均不能成为有效交付。至此，四个面的职责已经定义完整；下一节只说明
它们如何完成一次任务，不再引入新的组成层。

\subsection{外层能力晋级的操作阈值}

图\ref{fig:double-loop}已经给出外层反馈边；要使“能力扩大”成为可证伪命题，还必须规定一个环境改动
经历多少次复现、多少次跨合同复用和多长稳定窗口后，才允许从单次实现晋级为可复用能力。

对一次环境改动 $z$，原定义只要求规则进入真源 $R(z)$、接入可发现能力 $W(z)$、经正例和针对性
反例检验 $Q(z)$，并被后续业务实际复用 $A(z)$。这仍不足以回答“复现几次、复用几次、稳定多久”。
本文因此为后续审计预先冻结操作阈值 $\theta=(3,2,14\mathrm{d})$：同一版本能力在冻结输入和验收准则下至少有
3 次连续独立 replay；至少被 2 个不同 task contract 调用，且两个合同在模块、workload 或任务类别上
至少一项不同；从首次到末次合格调用跨越至少 14 天，并保持同一 artifact hash，或以显式新版本重新
资格化。外层能力扩展被重新定义为

\[
\operatorname{Ext}_{\theta}(z)=R(z)\land W(z)\land Q(z)\land A(z)
\land[n_{\mathrm{replay}}\ge3]\land[n_{\mathrm{reuse}}\ge2]
\land[\Delta t\ge14\mathrm{d}].
\]

这些数值不是从历史结果回算出的通过线，也不用于追认现有构件。三次 replay 用于排除一次性偶合，
两个合同用于区分“单任务可用”和“跨任务复用”。14 天也不是由本项目平均开发间隔拟合而来，而是
预先选择的两个七日观察周期：其目的只是避免把同一短时调试会话内的重复调用误写成跨轮稳定性。
因此，整组阈值只是兼顾审计成本与陈旧风险的工程启发式，不具有统计最优性，也不是跨项目定律。
后续评价还应报告 replay 阈值
$2/3/5$、复用阈值 $1/2/3$ 与稳定窗口 $7/14/30$ 天的敏感性。未达任一项的对象只能称为候选能力或
单次实现，不能进入有效能力集合。相应地，环境条件 $\Gamma$ 下的有效 Agent 能力写为

\[
\mathcal{C}_{\mathrm{eff}}(\Gamma;\theta)=
\{\mathcal{T}\mid\mathcal{T}\ \text{能在固定验收标准下形成某个}\ \mathcal{D},
\text{且新复用构件满足}\ \operatorname{Ext}_{\theta}\}.
\]

只有验收标准不变且
$\mathcal{C}_{\mathrm{eff}}(\Gamma_1;\theta)\subsetneq
\mathcal{C}_{\mathrm{eff}}(\Gamma_2;\theta)$ 时，才称环境能力扩大。当前主张映射尚未为每个历史构件完整
编码 replay 次数、复用次数和稳定窗口，因此本文不把纵向里程碑解释为这一严格集合关系已被证明；
它们只说明若干构件进入了后续任务。Token、代码行和脚本数量同样不能替代阈值审计。后文的双闭环
运行机制将在不增加新架构元素的前提下，形式化两条反馈路径的状态、触发条件和停止规则。

\section{四面的工程实例化：从方法接口到工作区载体}

\subsection{映射原则与边界}

四平面方法不要求使用某一种语言或目录结构。本工作区的参考实现选择 Markdown/JSON 表达专业知识与
机器合同，以 C 保存低开销任务生命周期，以 shell 连接工程工具，以 Python 实现合同校验、证据索引

\subsection{可执行领域环境：AM、NEMU、NPC 与 EDA 的协同关系}

Loop-Work 的四个责任平面只有落到真实工程对象上才构成领域 Agent。ysyx-workbench 中最基本的执行
闭环由 AM、NEMU 和 NPC 构成：AM 负责把 C/汇编程序、运行时和平台适配链接为同一 RISC-V 工作负载；
NEMU 在软件中执行该工作负载并给出参考架构状态；NPC 则以 Verilator 运行被开发的 RTL 处理器。
DiffTest（差分测试）在 NPC 每次退休指令后比较程序计数器、通用寄存器、浮点寄存器、确定性 CSR 和
特权态，使“参考语义”与“硬件实现”在同一程序身份上闭合。Yosys、OpenSTA 与开源 PDK 位于另一条
支路：它们不回答指令是否正确，而把同一冻结 RTL 转化为网表、面积和时序观测，使功能候选接受实现
可行性反馈。

图\ref{fig:workbench-domain-loop}给出这套环境的主数据流。它同时说明为什么缺少其中任一环都会削弱
Agent：没有 AM，测试程序和平台接口难以在参考端、目标端间复用；没有 NEMU，NPC 缺少独立的逐退休
参考；没有 NPC，软件模型无法成为 RTL 交付证据；没有 testbench、分层系统 workload 与 EDA 工具，
Agent 只能观察程序终态，不能定位周期合同或判断实现条件。

触发。该成本递增结构使 Agent 在局部修改时先使用低成本反例，在跨模块和系统风险出现时再升级验证。

\subsection{控制面的实现：生命周期、代次与门禁路由}

控制面位于目标合同与真实工程节点之间。它不负责实现 RTL，也不替代业务验证，而负责回答：当前
工作属于哪类任务、哪些路径由本轮拥有、哪些证据已经形成、何时需要独立复核，以及哪组固定门禁
能够授权终止。其上游是用户目标、分类策略和显式作用域；下游是图执行器、domain gate、证据面与
归档器。没有这一层，Agent 可以在多轮对话中继续修改，却无法机械区分“同一候选的复核”与“已经
产生新候选”。

参考实现采用一个轻量生命周期控制器。\taskpath{scripts/agent-flow.sh} 只是可移植启动适配器：仅当
C 源变化或缓存二进制不存在时，使用 \texttt{C11 -O2 -Wall -Wextra -Werror} 编译临时文件并原子替换；
真正的状态与门禁路由位于 \taskpath{scripts/agent-flow.c}。这种 C+shell 分工不是论文贡献本身，而是为
日常短任务降低解释器和全量 profile 开销的实现选择。\texttt{FlowMeta} 保存 task、class、archive
mode、status、耗时和 \texttt{generation}；后者承担旧证据失效语义：每次登记或再次触碰路径/门禁，
代次递增且状态回到 \statusword{ACTIVE}，只有 gate ID、状态和 generation 同时匹配的旧门禁结果才
允许复用。由此，新候选不能消费旧代次 PASS。承重实现节选集中于附录代码
\ref{lst:agent-flow-generation}，正文只保留该控制不变量。

生命周期操作的抽象语义如下。命令名只是参考接口：

固定 gate registry 不接受 Agent 临时拼接任意 shell 字符串；它把显式路径映射到已注册的验证入口。
因此，控制面只选择“哪一个既有判定器承担本次责任”，不能为获得绿色结果临时改写判定命令。任务
生成新路径、重新分类或补登记门禁时 generation 递增，旧候选缓存立即失效；只有同一代次的候选、
审查和正式结束可以复用门禁结果。这样，“完成”由 class policy、作用域、真实 evidence 和固定
checker 共同决定，而不是由模型自由解释。

附录代码\ref{lst:path-gate-routing}给出这一映射的三个真实分支。修改端到端配置时选择“执行剖面接线检查”，
修改任一 Skill 时选择“Skill 审计”，修改 RV64 子任务合同的规则、生成器或策略时还要增加“RTL 合同检查”。
因此，路径不是事后报告中的装饰信息，而是控制面选择验证责任的输入；固定门禁也不会因为 Agent 更换
措辞而变化。

\subsection{知识面的实现：专业知识如何编译为可执行能力}

知识面的关键不是存放更多 Markdown，而是把不同语义的知识放入不同载体，并沿固定编译链进入执行。
instruction 表达“什么不能被违反”，Skill 表达“怎样稳定地产生产物”，machine contract 固定“本次
允许读写与运行什么”，profile/E2E 表达“这些能力怎样组合才能证明完成”。它们的关系为

\[
\begin{aligned}
\text{professional invariant}&\rightarrow\text{executable procedure}
\rightarrow\text{task contract}\\
&\rightarrow\text{graph node}\rightarrow\text{domain evidence}.
\end{aligned}
\]

例如，接口策略要求在修改 RTL 前冻结握手、stall、flush/redirect、异常序、访存序和投机恢复；RTL
生成策略又要求先明确需求、状态机、不变量、数据通路与拓扑。任务 Skill 随后把这些义务参数化为
\texttt{allowed\_paths}、\texttt{write\_paths}、结构化
\texttt{command/mode/purpose}、success criteria 和反例出口。若发现范围不足，子节点只能请求新版本
合同，不能通过一句补充说明改变旧边界。profile 再把合同绑定到 owner、函数、输入输出和依赖闭包，
最后由真实 testbench、DiffTest、系统或 EDA 节点承担业务结论。

\subsection{执行面的实现：确定环境、图闭包与节点作业}

执行面的参考实现把知识面选出的 profile 展开为有序节点，并为每个节点建立确定的工具环境。其物理
主链到“产生原始观测”为止；report、manifest 和 publication 属于下一节的证据面，不能因为它们由同一
runner 调用就混成一个职责。

\begin{lstlisting}[language={},numbers=left,
  caption={profile 从任务身份到原始节点观测的执行主链}]
task_slug + selected profile
  -> rebuild active live index
  -> brief(non-history focus, bounded budget)
  -> recursively resolve @include profile closure
  -> bind node/module/function/owner/inputs/outputs
  -> load deterministic tool environment
  -> dispatch node function
  -> raw evidence/<node_id>.log + rc + runtime state
\end{lstlisting}

图执行器只承担通用编排，不把全部工程语义塞入一个 shell。profile 使用
\texttt{node/module/function/owner/inputs/outputs} 六元组；\texttt{@include} 递归展开可复用子图；
module library 实现具体节点函数。\taskpath{scripts/agent-env.sh} 在所有非交互节点之前固定仓库根、NEMU、
AM、NPC、Yosys/STA、RISC-V 工具链与可选 JDK 路径，\taskpath{scripts/agent-run.sh} 将同一环境提供给
手工或单节点命令。因此，profile 的上游是机器合同与能力索引，下游是具有确定环境的 domain command，
而不是另一个自然语言规划器。

\subsection{证据面的实现：资格化、失败关闭与原子发布}

\subsubsection{长跑终止语义适配器}

长时间仿真、综合、STA 或系统回放的进程状态只属于执行面；工程 PASS 属于证据面。Loop-Work 因而
规定一个最小提交条件：

\[
\mathrm{PASS}=C_{\mathrm{run}}\land C_{\mathrm{evidence}}
\land C_{\mathrm{cleanup}}\land \neg C_{\mathrm{signal}},
\]

其中 $C_{\mathrm{run}}$ 表示主命令正常结束，$C_{\mathrm{evidence}}$ 表示规定 marker、哈希和检查已到
末端，$C_{\mathrm{cleanup}}$ 表示配置恢复与临时资源清理成功，$C_{\mathrm{signal}}$ 表示收到 HUP、INT
或 TERM。进程返回 0 只是第一个条件，不能单独提交工程状态。

\subsubsection{证据原子发布、有界召回与方法自验证}

证据提交以后仍不能直接进入长期知识。发布器把节点标识、来源执行剖面、实现模块、责任主体、函数、
状态、输入、输出和证据路径组成节点元组，再与原始观测及运行身份绑定；对应机器字段为
\path{node/source-profile/module/owner/function/status/inputs/outputs/evidence}。系统依次生成节点表、
调度日志、任务报告、清单和证据索引；随后重算普通证据的路径、尺寸与 SHA-256，验证执行剖面闭包和
事件顺序，最后才生成完成标记。完成态先同步暂存文档，再在单个数据库事务中复核完成标记、发布记录
与产物集合；任何净化、索引、哈希或数据库步骤失败都会撤销本轮发布。参考实现主要位于
\taskpath{scripts/e2e/lib/report.sh}，但其抽象职责是“证据原子提交”，不是格式化报告。

下一轮只从已发布对象中选择最小充分历史。当前有效的 instruction、Skill 和执行剖面保持在线；稳定
memory 与任务档案可查询；原始日志只向上下文提供路径、尺寸、SHA-256、标记和有界摘要。启动摘要受
执行剖面、非历史主题和 2400-token 硬预算约束；历史运行通过 run-id 与证据索引按需读取。这样，
证据面可以向知识面反馈已验证结论，而不会把全部聊天和重型日志再次灌入模型。

方法自身同样接受分层验证。轻量模式只检查控制器与 shell 状态协议；目标级模式追加 schema、policy、
artifact、Skill、合同和 profile 绑定审计；release 模式再构建相对路径包、扫描本机路径与私有 marker，
并复核数据库与交付边界。参考实现由 \taskpath{agent-maintain.sh} 编排，并由
\taskpath{package-ai-dev-env.sh} 形成可迁移包。两者位于外层能力闭环的末端：只有规则、执行入口、反例
gate 和交付包同时成立，一项环境修改才算从个人经验变成可复用工程能力。

\section{四面协同的双闭环运行机制}

顶层方法已经定义四类责任状态和两条返回路径，前一章给出了同构参考实现。本章只在时间轴上形式化
这些既有接口：
内层闭环优化当前任务，外层闭环把重复且可迁移的缺口固化到控制、知识、执行或证据面。双闭环不是
新的架构层，也不改变四面的职责边界。

\subsection{状态、事件与反馈对象}

本文把第 $k$ 个工作轮的状态写为

\[
x_k=(D_k,C_k,V_k,L_k,P_k),
\]

其中 $D_k$ 为设计快照，$C_k$ 为配置与输入身份，$V_k$ 为验证器/oracle 版本，$L_k$ 为未闭合义务
账本，$P_k$ 为当前成熟度。这只是状态记录的类型定义，并不是预测模型。本轮合同冻结有限验收谓词
集合 $Q_k=\{q_1,\ldots,q_n\}$，并为每个谓词给出期望状态 $\hat{o}_k(q)$。真实工具产生的观测状态
限定为

\[
o_k(q)\in\{\mathrm{PASS},\mathrm{FAIL},\mathrm{GAP},\mathrm{UNQUALIFIED}\}.
\]

身份不一致、证据不完整和 freshness 失效形成 blocker 集 $B_k$；本轮未闭合项被操作性地定义为

\[
E_k=\{q\in Q_k\mid o_k(q)\neq \hat{o}_k(q)\}\cup B_k.
\]

\statusword{BLOCKED} 不是工具观测值，而是 $B_k\neq\varnothing$ 时控制面对下游消费作出的阻塞裁决。
这里没有抽象的“差值”或待学习的反馈函数：$o_k$ 必须来自编译、仿真、testbench、综合/STA、退出
状态、计数器或身份哈希；$E_k$ 的每一项必须能回指原始观测。动作选择遵循固定优先级。若
$B_k\neq\varnothing$，保持 GAP 且不猜测性修改 RTL；若候选触发 hard gate，先回滚并复验；若确认是
oracle 缺陷且原始日志完整，只生成版本化 replay；其余情况从能够区分现有竞争假设的实验中，按
focused、module、system、PPA 的成本层级选择最低层实验，同层并列时采用合同中预先登记的顺序。
$x_{k+1}$ 是动作执行后由收据记录的新状态，而不是公式预测值。由此，反馈规则可以由另一位工程师按
相同合同复核，无法判别时则保持 GAP。

\subsection{内层算法与停止条件}

\begin{lstlisting}[language={},numbers=left,float=htbp,
  caption={Loop-Work 的最小执行算法}]
x <- bind(design, config, inputs, oracle, maturity)

while budget_available:
    r <- freeze_scoped_claim_and_gates(x)
    open <- classify_unmet_gates_and_blockers(x, r)
    a <- select_by_gate_priority_then_cost(open, contract_order)
    y <- execute_and_observe(x, a)
    A <- seal(identity, commands, rc, raw_output, y)

    if identity_mismatch(A) or evidence_incomplete(A):
        return GAP(A, "binding/evidence")

    e <- compare(r, y)
    if violates_hard_gate(e):
        rollback_to_last_qualified_state()
        verify_rollback()
        record(REJECTED_OR_ROLLED_BACK, A, e)
        continue_or_stop()

    if scoped_error_is_zero(e):
        if promotion_requested and parent_gates_pass_same_identity(A):
            return PROMOTED(A)
        return SCOPED_ACCEPTED(A, promotion=false)

    if error_is_actionable(e):
        x <- transition(x, a, e)
        continue
    return GAP(A, e)
\end{lstlisting}

算法强调三个不等式：

\[
\text{SCOPED\_ACCEPTED}\neq\text{PROMOTED},
\]
\[
\text{replay PASS}\neq\text{raw live-run PASS},
\]
\[
\text{benchmark completed}\neq\text{measurement qualified}.
\]

\[
\begin{gathered}
\text{engineering counterexample}\rightarrow\text{stable rule extraction}\\
\rightarrow\text{instruction/Skill/checker}\rightarrow\text{profile wiring}\\
\rightarrow\text{qualified execution}\rightarrow\text{next engineering action}.
\end{gathered}
\]

这种分流避免两种相反错误：其一，把所有历史过程塞进 memory，使下一轮被过时细节淹没；其二，只在

拒绝错误输入，则处于“能跑但不会判”。只有闭合这两个缺口，工程经验才形成 Agent 可执行、可检验的
外部能力。

失败、回滚和未晋级也是有效产物。它们排除了一个候选方向，保护了基线，并为下一轮提供更窄的搜索

\subsubsection{架构发现、闭合与稳定}

架构发现不是泛读整个仓库，而是围绕准备优化的事务建立可验证的生产者—消费者图。例如 memory
stall 的 CPI 候选必须先回答：请求由哪个模块建立，reservation、bridge、AXI response 和 commit 各由
哪个 owner 持有，flush 或 replay 能否清除它，以及哪个计数器能观察到每个生命周期。输出是带路径和
未知项的债务表，不是 RTL 候选。

架构闭合逐项处理这些债务，并把历史系统缺陷下沉为低成本检查。若一项 Linux 故障可以由模块 TB 或
断言稳定复现，后续 Agent 就不必用完整 Ubuntu 回放筛掉同类候选；若只能在系统组合中出现，则保留在
系统层而不伪造低层覆盖。架构门要求功能回归、双发射/乱序合同、精确恢复、异常与副作用同时闭合，
并用能够通过编译的负向 RTL 检查判定器是否真的对目标错误敏感。只有 production RTL 与配置冻结后，
才形成 \statusword{ARCH\_STABLE}；它表示性能测量的架构前提稳定，不表示 PPA 已经合格。

\subsubsection{量测合同与性能基线}

正式测量首先冻结 workload 二进制、输入、编译器、起止 PC/marker、cache/TLB 初态、memory latency、
seed、计数器版本、重复次数和阈值。基本量为

\[
\mathrm{CPI}=\frac{\text{测量窗口内的核心周期数}}
{\text{测量窗口内退休的架构指令数}},\qquad
\mathrm{IPC}=\frac{1}{\mathrm{CPI}}.
\]

双发射核每周期有两个退休槽。令 $C$ 为冻结 ROI 的核心周期数，$R>0$ 为退休指令数，
$l_s,l_e\in\{0,1\}$ 分别为日志裁剪起止端点的 lane 编号。若裁剪协议把可见槽跨度定义为

\[
S=2C+l_e-l_s,
\]

且 $U_{\mathrm{span}}=S-R$ 为该裁剪跨度内的未使用槽，则由
$2C=R+U_{\mathrm{span}}+l_s-l_e$ 可得

\[
\mathrm{CPI}=\frac{C}{R}
=\frac{1}{2}+\frac{U_{\mathrm{span}}+l_s-l_e}{2R}.
\]

因此，原先不含端点项的写法只有在 $l_s=l_e$，或把
$U_{\mathrm{corr}}=U_{\mathrm{span}}+l_s-l_e=2C-R$ 明确定义为“端点修正后的未使用槽”时才成立：

\[
\mathrm{CPI}=\frac{1}{2}+\frac{U_{\mathrm{corr}}}{2R}.
\]

为避免 lane 被误解为半个物理周期，新的量测合同优先使用固定半开周期窗口 $[c_0,c_1)$，令
$C=c_1-c_0$、$U_{\mathrm{full}}=2C-R$；此时上式直接成立且不再需要端点 lane。旧 A1/A2 日志仍按
其原裁剪协议重放，但收据必须显式保存 $l_s,l_e,U_{\mathrm{span}}$ 与 $U_{\mathrm{corr}}$，不能混用。

本工程中的 A1 是第一次原始性能基线执行，A2 是同一冻结配置下的第二次独立执行。二者都被旧判定器
因 Dhrystone 的 ROI 从 lane1 结束、在 lane0 重新开始而拒绝；原始状态至今保持 FAIL。后续版本化勘误
只把错误的“起止 lane 必须相等”代理条件替换为上述精确容量式，并对冻结 A2 日志重放；设计、workload、
ROI、原始日志和旧状态均未改变。CoreMark 与 Dhrystone 各三次统计开启运行 bit-exact，统计关闭运行的
cycles/retired 又与开启时相同，才形成 \statusword{PERF\_BASELINE}。这组证据证明量测接口可重复且
统计逻辑没有观察到干扰，不证明 CPI 已经因某次 RTL 修改而改善。

\subsubsection{瓶颈普查、单机制候选与反馈}

性能基线形成后，Agent 才能建立 lost-slot census（退休槽损失普查）。总 cycles、unused retire slots、
I/D-cache miss、控制等待、LSU 等待、AXI 等待和事务 owner 驻留分别记录；这些计数可能在同一周期重叠，
不能简单相加为总周期。每个主瓶颈必须附带竞争解释，并预测“若主假设成立，哪个 workload、哪个 counter、
哪个事务阶段会怎样变化”。控制面优先调度能区分两种解释的最低成本实验，而不是直接要求模型改 RTL。

一个候选只允许包含一个可归因机制，并按同一 design/build/workload 身份执行交错 A/B，例如
A--B--B--A--A--B；每次原始日志独立保存，比较逐 workload 的中位数、最差值和守恒项。候选若改变周期、
资源数量、调度、恢复或事务生命周期，就被重新分类为架构变更并返回架构门。本工程中，放宽双 memory
发射使 CPI 从 0.645 退化为 0.665，候选被回滚；另一次只读 owner 探针虽然完成六次 benchmark，
但事件身份全部无效，因此控制面没有生成 production RTL candidate。这两个结果分别证明负优化和无效
诊断不会因“程序跑完”而进入下一节点；它们不证明所有未来瓶颈均能由现有计数器识别。

\subsubsection{PPA 资格、系统再认证与可交付边界}

联合资格按固定全序裁决：同源设计与完成定义、功能、双发射/乱序、精确恢复与副作用、精确 timing
tier、逐 workload floor、面积/功耗资格、Pareto 前沿，最后才执行晋级检查。所谓 Pareto 前沿，是不存在
另一个设计点在 CPI、频率、功耗和面积上均不差且至少一项更好的候选集合。平均 CPI、generic cell 数
或一个综合评分不能抵消前面的硬门。

物理资格至少要求同源 netlist、SDC、library/corner、完整 I/O delay、真实 memory macro、有效切换活动、
时钟树/寄生与对应 timing 报告。当前 Yosys/OpenSTA 结果能够用于结构筛选，却因 I/O 未约束、缺少
SPEF、CTS、OCV、真实宏和功耗活动而保持 \statusword{UNQUALIFIED}。这种非晋级状态不是“尚未整理
好的成功”，而是一个可消费的工程结论：允许继续定位面积或逻辑深度，不允许宣称频率、面积、功耗
签核，也不允许进入系统再认证和可重复 promotion。

因此，本节证据支持的是“工作流能把量测错误、负优化、无效归因和物理条件不足导向不同终态”，并
形成下一实验所需的输入；它尚不支持“该方法已经带来稳定 CPI 提升”或“当前核已经完成物理 PPA
签核”。这种区分使性能工程的有效产物不仅包括更优设计，也包括被可靠淘汰的候选和不能晋级的边界。

\section{案例研究设计与证据协议}
\label{sec:case-design}

前述章节给出了方法及其实现接口；在进入工程里程碑之前，本章先固定“哪些材料可以作为证据、怎样
选择和编码主张、冲突怎样处理”。这样，后文的时间顺序只用于过程追踪，而不会被直接解释为方法产生
效果的因果顺序。本文采用单仓库纵向嵌入式案例研究，并借鉴软件工程案例研究和过程追踪对案例边界、
分析单位与诊断性证据的要求\cite{runeson2009casestudy,beach2019processtracing}。

\subsection{案例边界与分析单位}

案例是持续演化的 RISC-V 处理器工作区；分析单位不是目录、文件或一次聊天，而是任务 episode 中可
独立判真的工程主张。一个 episode 具有明确目标、待判断对象、可恢复验收条件，以及 accept、reject、
rollback、GAP、UNQUALIFIED、interrupted 或 MISSING 中至少一个终态。观察窗为
2026-04-01 至 2026-08-04，数据冻结提交为
\path{858fd3cf0dc6cb466c80707051f40d4a4710fcbc}。版本化源码、合同、task-run 状态、原始日志、
结构化收据和证据哈希进入分析；只存在于未归档对话中的推测不进入证据集。

\subsection{主张选择、编码与冲突处理}

30 条目的性主张由任务终态、里程碑和阶段性报告抽取，并统一规范为“工程对象---实验身份---验收
谓词---结论---边界”五元组。重复发布合并为一个 episode，强弱不同或互相矛盾的主张分别保留，再按
RQ1--RQ4、验证压力、正负结果与证据状态作最大差异选择。纳入项必须可被反驳、有精确来源路径、能
恢复至少两类身份/执行信息，并具有明确的接受、拒绝、回滚或未资格边界；纯进度文字、配置不可比的
数字和无法恢复决策边界的临时日志被排除。该集合用于审计本文实际使用的论断，不作为任务总体的概率
样本。

机器可读 codebook 把字段分为五组：主张与分类，episode 与身份，来源与执行，结果与反例，以及外推
边界。证据状态只允许 SUPPORTED、PARTIALLY\_SUPPORTED、OBSERVATIONAL\_ONLY、CONTRADICTED
和 MISSING。只有在 design、configuration、workload 与 oracle 适用域相同而结论不同时，才构成证据
冲突；新判定器可以生成版本化 replay，但保留原始状态。

第二 Agent 对预先固定的 12/30 主张执行隔离、只读的反例复核，检查状态、原始路径、数字、返回码、
回滚和声明边界。复核者能够看到主编码，因而这是独立反例审查而非盲法双编码；三条初始主张因环境
描述过强、身份冲突或原始路径不足被阻断并修订。样本规模和非盲条件决定本文不报告人类编码一致性
指标\cite{oconnor2020intercoder}。

\subsection{数据保留与可复核入口}

公开仓库为 \href{https://github.com/mcsaver/oscpu}{mcsaver/oscpu}，机器可读主张表、选择协议、独立
复核和构建入口分别由
\taskpath{claim-evidence-map.tsv}、\taskpath{case-selection-protocol.md}、
\taskpath{independent-claim-review.tsv} 与 \taskpath{paper-reproduction.md} 承担，完整相对路径和
schema 见附录~\ref{app:claim-evidence}。可版本控制的合同、状态、收据、摘要、索引和哈希直接保留；
重型日志或波形由 manifest 记录路径、尺寸、SHA-256、时间和 marker。原始对象丢失时登记 MISSING，
受访问限制时登记 RESTRICTED，二者均不由摘要替代。

早期 episode 缺少统一的模型快照、seed、采样参数、完整系统提示、工具序列、上下文截断状态和部分
重型原始对象。这些记录仍可说明接口如何演进，但不进入模型级复现、效率比较或严格总体率的分母。
由此固定证据协议后，下一章才沿验证压力追踪方法如何从 RV32 局部运行扩展到 RV64 系统事务与 OoO
性能资格化。

\section{需求驱动的方法演进与工程里程碑}

\subsection{验证压力与环境能力的共同演进}

早期把“环境建设”和“芯片开发”混在同一条非结构化对话中，会产生三个直接问题：修改 RTL 后无法
判断旧日志是否仍属于当前设计；系统启动现象容易被概括为超过证据层级的结论；反复出现的调试经验
仍停留在个人上下文，下一任务只能重新发现。Loop-Work 将二者通过合同接口分开：芯片节点只负责形成
当前设计的候选和业务证据，环境节点只负责把已验证且可迁移的规则、Skill、执行入口和证据协议版本化；
两者通过有类型的输入输出相连，而不共享模糊的“完成”状态。

这种拆分没有形成两条互不相关的路线。每当处理器任务暴露稳定失效模式，外层闭环就增加一个可复用
环境能力；新能力随后缩小下一类任务的可执行范围，并提高其证据要求。表\ref{tab:milestone-ladder}
按验证压力列出这种共同演进。它支持“同一接口在更强任务上持续形成可追踪产物”的过程结论，不构成
某个环境构件单独提升生产率的因果实验。

\subsection{从静态候选到局部动态语义闭合}

早期冻结记录包含 RV32I 非流水线 \texttt{NpcCore} 与 8 个辅助 RTL 文件。Verilator lint 通过，但没有
testbench、镜像和参考对拍，因而只能接受“语法与静态结构成立”。随后的动态接通任务把 AM hello image、
DPI/C++、pmem、串口和退出码 0 连接起来，并继续增加 itrace、mtrace、dtrace 与批量重放。Agent 的介入
由“一次生成候选”变为“生成---运行---
观察---修正”，工程师则开始把隐含的完成定义写成可执行接口。

该组证据的有效范围是最小动态闭环，而非完整 ISA、异常或 DiffTest；其方法意义在于把 lint 之后仍
缺少的运行接口显式转化为下一轮输入。

相关记录已经出现有界历史检索、子 Agent、独立复核与任务档案等协作结构，但这些结构尚未同 AM image
构建、target/reference、动态 oracle 和可执行完成门连接成统一数据流。人的主要工作仍包括解释运行输出
和决定能否接受；Agent 虽能生成、复核并参与短反馈，却不能依据统一合同独立形成动态语义收据。正是
lint PASS 与运行闭环之间的落差，促使后续把 image build、reference、target、compare 和 record 固化为
图节点，并把“没有动态证据就不得宣称功能成立”写成 instruction。第一项环境扩展扩大的是执行与解释
最小 CPU 事务的闭合能力，而不是从零开始建立所有 Agent 协作结构。

这一里程碑的证据上限是给定 hello 镜像的最小运行语义；完整 ISA、异常、DiffTest 和 RV64 功能由
后续层级继续验收。

\subsection{target/reference 闭合：从 RV32 single 到 RV64 SoC}

随后，\taskpath{npc/sim} 被设计为统一入口，按配置分流 \taskpath{npc/single} 与
\taskpath{npc/soc}。SoC 数据路径为：

\begin{lstlisting}[language={},numbers=none,
  caption={RV32 SoC 的 target/reference 数据流}]
am-kernels -> AbstractMachine(riscv32-ysyxsoc image)
-> npc/sim(BACKEND=soc) -> npc/soc -> ysyxSoCFull
                       \-> NEMU(CONFIG_SOC_SIM) reference
-> commit-level DiffTest
\end{lstlisting}

SoC 接通又暴露出另一类环境问题：同一个“运行测试”动作可能在 NEMU reference、NPC single、NPC SoC
上具有完全不同的地址图和结论。这个经验后来进入 E2E 场景隔离规则：\texttt{nemu-dev*} 展开后只允许
NEMU/software-flow 节点，\texttt{npc-dev} 只允许 NPC/software-flow 节点，而显式 integrated profile
保留跨栈闭环；\texttt{--validate-profile} 与真实 dispatch 共用边界检查。这样，profile 不是把模块分开
管理，而是防止一个平台的 PASS 在数据流中被误送给另一个平台。

MROM 入口为 \texttt{0x20000000}，SRAM 为 \texttt{0x0f000000..0x0f001fff}；cpu-tests 形成
39/39 DiffTest，\texttt{char-test} 观察 UART，\texttt{mem-test} 在
\texttt{PC=0x200002c6} 到达 GOOD TRAP。这里的关键产物不是另一个 CPU 文件，而是同一镜像在 target
与 reference 两侧可比较。

随后 NPC 先扩展 PC/GPR/CSR/AXI/DPI 到 RV64，关闭尚未资格化的 cache 与 DiffTest，得到 38/38。
NEMU 补齐 RV64 CPU state、CSR 与 RV64I/M/B/C/W reference 后，形成 40/40 和 CoreMark DiffTest。
这两个冻结点必须区分：38/38 说明 NPC 在给定自测中运行，40/40 才增加 target/reference 一致性证据。

从 32 位扩展到 64 位还改变了 Agent 的上下文组织方式。PC/GPR/CSR/AXI/DPI 不再适合由一个宽泛任务
同时修改，局部 reviewer 也不能只读主 Agent 的摘要。为此，后来的 RTL task Skill 将 RV64 子任务拆为
\texttt{read-only-review}、\texttt{implementation}、\texttt{verification} 与 \texttt{ppa-analysis} 四类，
要求合同显式列出 RTL、spec、TB、
evidence、写路径和命令，并让子 Agent 在隔离上下文中工作。它没有减少源码探索；相反，它使多 Agent
能够并行复核不同债务项，同时保证每个结论仍能追溯到具体 module/signal/transaction 与测试配置。

39/39 与 40/40 的证据范围分别绑定各自冻结测试集和配置；SoC 全量、Linux、FPGA、物理芯片与跨位宽
性能属于更高层验收。

\subsection{系统级闭合：NEMU、NPC 与十九小时 Ubuntu 事务}

系统级研究先以 OpenSBI v1.8、内嵌 DTB 和 S-mode mini payload 形成固件交接；
mini payload 的“\texttt{S}”
与 GOOD TRAP 只证明 M-mode 到 S-mode handoff，不等于 Linux。随后，NEMU reference 先进入 Ubuntu
22.04.5 的非交互 shell，NPC 则到达 2 GiB virtio block、EXT4 rootfs、systemd PID1 和 Ubuntu banner。

如果没有证据分层，以上现象很容易被统一写成“Ubuntu 已启动”。
\taskpath{.github/instructions/rv64-linux-bringup.instructions.md} 因而把路径拆成
\texttt{env-built}、QEMU reference、OpenSBI handoff、kernel progress、init executed、Ubuntu probe、
initramfs shell 与真实 rootfs 八级；\taskpath{.github/instructions/virtio-rootfs.instructions.md} 又要求 virtio-mmio register、
vring descriptor/avail/used、host block backend、UART/virtio 多源 PLIC、DTB、kernel config、\texttt{/dev/vda}
和 mount 证据同时闭合。rootfs 模板必须按内容寻址复制为 run-owned 工作副本，模板前后 SHA 保持不变，
guest 合法写入只能改变副本。instruction 在这里直接改变了日志的解释方式：NEMU shell 与 NPC banner 被
保留为不同层级，而不是由 Agent 用更顺耳的自然语言合并。

表\ref{tab:linux-evidence-levels}展示该 instruction 的承重内容。八级不是八条近义描述，而是八个不同
验收谓词；上一级的产物只能作为下一级输入，不能自动继承更强结论。例如，QEMU 通过只证明镜像和

\subsection{跨模块事务合同：排空、FENCE 与 memory owner}

\taskpath{OooPendingDrainResolveGate.v} 的三个不可变快照展示了工程合同如何从隐含条件变成可验证
owner 边界。

这一演化由两层环境共同约束。接口 instruction 先要求回答“谁产生 stop、谁保持 outstanding、哪类
flush 可以清什么、已发 AXI 和 committed store 是否仍有 owner”；RTL instruction 再要求把需求、状态机、
不变量、数据通路与同拍优先级写清。具体复核节点则由 task Skill 限定到该 gate、CoreGlue/ControlPlane
连接、相关 testbench 与证据路径，并保留 scope extension。于是 Agent 不是看到一个布尔表达式后继续
叠加条件，而是必须解释每个条件对应的 transaction lifecycle 与反例。

\noindent\begin{minipage}{\dimexpr\linewidth-2.4em\relax}
\begin{lstlisting}[language=Verilog,numbers=none,
  caption={快照 A：基本后端排空}]
assign backend_drained_o = (rob_count_i == 0) &&
                           (issue_count_i == 0) &&
                           (core_retire_count_i == 0) &&
                           !synth_lane1_ret_pending_i &&
                           !synth_lane1_branch_drop_pending_i;
\end{lstlisting}
\end{minipage}

快照 A 将 ROB、issue queue、当拍退休和 synthetic lane1 pending 合取为 drain；它没有显式表示退休
store 仍驻留 SQ 的情况，也没有完整 memory owner 静默条件。快照 B 增加
\texttt{mem\_retire\_quiet\_i}，并根据合法状态域证明 \texttt{rob\_count==0} 蕴含
\texttt{retire\_count==0}，删除冗余条件：

\begin{lstlisting}[language=Verilog,numbers=none,
  caption={快照 B：退休/SQ 静默与冗余条件消除}]
// commit0_fire -> count_q != 0
// commit1_fire -> commit0_fire
// therefore rob_count == 0 -> retire_count == 0
assign backend_drained_o = (rob_count_i == 0) &&
                           (issue_count_i == 0) &&
                           !synth_lane1_ret_pending_i &&
                           !synth_lane1_branch_drop_pending_i &&
                           mem_retire_quiet_i;
\end{lstlisting}

该切片对 16-entry ROB 的有限二值合法域枚举 2176 个用例。枚举器不是把随机输入跑 2176 次，而是先用
\texttt{commit1\_fire -> commit0\_fire}、\texttt{commit0\_fire -> count\_q!=0} 和
\texttt{commit valid=commit fire} 排除不可达组合，再比较删除前后谓词。附录表
\ref{tab:rob-legal-domain-examples}给出其中五类代表状态；正文只保留其语义边界：ROB 空、head 阻塞、
单退休、双退休和“lane1 独立退休”这一被排除的非法组合。

\begin{lstlisting}[language=Verilog,numbers=none,
  caption={快照 C：ordinary FENCE 等待完整 memory owner 静默}]
wire pending_fence_mem_quiet_w =
    !pending_system_fence_i || mem_idle_i;

assign drain_complete_o =
    stop_pending_i && backend_drained_o &&
    pending_control_ready_i && !pending_replay_wait_o &&

\subsection{反例驱动的候选淘汰与搜索空间收缩}

一次双 memory 放宽使同配置 CPI 从 0.645 退化到 0.665，候选被回滚；branch+ret 虽通过 focused
test，Verilator 随后报告 \texttt{UNOPTFLAT} 组合环，同样回滚。打开分支推测后，局部 ROB-walk
测试可以通过，但全核形成“branch speculation 冻结 commit---JALR 等待 backend drain---drain 等待
ROB 排空”的环形等待。spec-on 的 riscv-tests 为 255 PASS/16 FAIL、AM 为 25 PASS/32 FAIL；回退
mode=0 后 riscv-tests 271 PASS/0 FAIL、module 113/113 PASS。

同一反馈纪律也出现在 NEMU，而不只在 NPC RTL。\texttt{nemu-ubuntu-profile} 将 basic block、wide ifetch、
decode cache、host-vaddr fast path、Sv39 TLB 和诊断 counter 做成显式 runtime flags；detail counter 默认
关闭且默认 run 要求其为 0，从环境层保证“用于定位的探针”不自动成为性能基线。一个 64K
decode-cache detail run 将 hit rate 提到 94.52\%，但得到 43.19 MIPS，低于同容量 default run 的
43.57 MIPS，工作区据此保留“容量 footprint 抵消 miss 减少”的负结论；只提前识别
\texttt{c.sdsp/c.ldsp} 的 RVC stack fast path 为 44.31 MIPS，也低于相邻 baseline 46.95 MIPS，候选撤回。
这些 host MIPS 受 WSL 波动影响，不能跨 run 任取峰值作稳定收益；但 profile 的开关、counter 非干扰和
相邻反例使“继续扩大 cache/只优化单条压缩指令”成为可审计的被拒方向。这里，E2E 既调度真实系统
workload，又把负实验转成下一轮 Agent 不应重复的搜索边界。

在后续定向回归中，IFU、FENCE、STORE/AMO 共 23 个 compile-success 负向 RTL 变体被判定器动态拒绝
（19+2+2）。这些结果不证明全状态空间正确，却证明在指定 fault set 内，测试不是只能对当前正确版本
打印 PASS。对工程师而言，回滚是一项带复验证据的候选淘汰结果；对 Agent 而言，它把下一轮搜索
限制在仍然满足基线合同的空间内。

这些回滚把给定配置下的不合格方向从后续搜索空间中排除；保留基线的全局最优性和未建模回归仍是
独立问题。

不合格 owner 量测和代理 PPA 越级被相应门禁拒绝。由于没有对照组，本文不推断因此节省了多少人时、
算力、缺陷逃逸或上市周期。

\subsection{当前 30 条主张的描述性审计}

\taskpath{docs/research-paper/claim-evidence-map.tsv} 的冻结 SHA-256 为
\path{f20a63ce701d31703f9fe3615d9bb7ae45c134b8b681293c1d98515facf7ab7a}。30 条主张中有 18 条
SUPPORTED、4 条 PARTIALLY\_SUPPORTED、1 条 OBSERVATIONAL\_ONLY、6 条 CONTRADICTED、1 条
MISSING。CONTRADICTED 不等于“系统失败六次”：其中包括论文主动构造并由现有证据反驳的强命题，
例如“代理 STA 已证明 200 MHz 物理签核”。同理，SUPPORTED 是逐条主张状态，不是方法成功样本。

为把当前审计和未来实验使用同一指标语言，令 $C_i=1$ 表示 Agent 声明完成，$Y_i=1$ 表示独立隐藏
oracle 的全部强制门通过，$P_i=1$ 表示结果已发布或晋级，则严格指标为

\[
\begin{aligned}
\mathrm{FCR}&=\frac{\sum_i[ C_i=1\land Y_i=0]}{\sum_i[C_i=1]},\\[0.55em]
\mathrm{VSR}&=\frac{\sum_i[Y_i=1]}{N},\\[0.55em]
\mathrm{UPR}&=\frac{\sum_i[P_i=1\land Y_i=0]}{\sum_i[P_i=1]}.
\end{aligned}
\]

表\ref{tab:current-metric-qualification}把三个指标先用于当前主张表的资格审计。结果不是填入一个看似
精确的百分比，而是确认现有字段能否构成合法分子和分母。

\subsection{尚未执行的 B0--B3 受控对照与组件消融}

现有纵向材料用于检验接口能否实例化，尚不能识别 Loop-Work 相对直接提示或一般工具 Agent 的因果
增益。后续实验因此预注册四个递增条件：B0 为冻结提示的一次生成，B1 加入受预算约束的工具反馈与
迭代，B2 再加入有界召回、任务合同和显式成功条件，B3 最后加入实验身份、证据新鲜度、mutation、
rollback 与原子发布。任务按局部功能、跨层逃逸、性能回退、身份错误、半发布和控制事务等风险分层，
在同一模型、预算、初始提交和执行后端下随机分配；隐藏 oracle 与 mutation 集由被测工作流之外的
过程预先冻结。

B0--B3 只估计逐级组合包。P1--P4 的单项归因还需要在 B3 上分别移除身份、负向资格、状态提交或晋级
约束，并保持其余组件不变。正式样本量、主要指标 FCR、次要指标 VSR/UPR、盲审、固定停止规则和
缺失值处理将在不观察正式结果的前提下预注册；当前 512 次仅是资源规划值。完整实验矩阵已经保存在
公开的 \taskpath{experiment-plan.md}，本文不把计划写成已完成结果。

\subsection{构念、内部、外部、结论与复现效度}

\begin{enumerate}
  \item \textbf{构念效度：}证据完整不等于 RTL 正确，拒绝假 PASS 也不等于提高最终功能成功率；
  ARCH\_STABLE、PERF\_BASELINE 和 PPA 资格是不同构念。FCR/VSR/UPR 在缺少 $C,Y,P$ 字段时保持
  UNQUALIFIED，避免用主张状态替代隐藏真值。
  \item \textbf{内部效度：}模型、任务难度、RTL、验证平台和开发者经验同时演进。A3、mutation、
  rollback 与 owner FAIL 能建立诊断性过程链，但不能识别 Loop-Work 的独立因果贡献；每个里程碑只
  说明相应接口在该压力层级被实例化。
  \item \textbf{外部效度：}当前材料来自一个 RISC-V 仓库和一位主要开发者。NEMU、NPC、Yosys 与
  OpenSTA 增加了后端和压力类型差异，却不构成跨团队、跨 HDL 或商业项目复制。
  \item \textbf{结论效度：}30 条主张为目的性审计集，12 条复核由非盲第二 Agent 完成，既不是随机
  样本也不是人类双编码。状态比例只能描述本表，不能外推总体成功率；未来 512 次仅为初始资源设计
  目标，正式样本量以预注册功效分析为准。
  \item \textbf{判定器与系统边界：}mutation 只覆盖声明且非等价的 fault set；A3 只覆盖指定
  design/config/rootfs 与系统事务；当前 PPA 缺少完整 I/O、SPEF、CTS、OCV、真实 memory macro、
  power activity 和多 PVT，统一保持 UNQUALIFIED。
  \item \textbf{复现与维护效度：}工程证据和冻结 oracle 可以重放，但早期模型、seed、temperature、
  上下文及部分 raw payload 不完整，商业模型采样轨迹不能重建。合同、checker、identity 与索引还需要
  持续维护；当前没有跨项目成本分母，不能宣称其净收益。
\end{enumerate}

因而，当前案例研究回答的是“Loop-Work 能否把特定工程状态转化为可审计主张，以及现有记录支持哪些
有限命题”；B0--B3 及单组件消融才用于回答“这些构件是否导致更低假完成率或更高可交付率”。两类
证据承担不同的推断责任。

\section{未闭合工程目标如何继续约束 Workflow}

RV64 双发射完整 OoO 核的未闭合目标被写成一组后续 Workflow 义务：架构债务识别与闭合、历史缺陷
回归下沉、architecture gate、arch-stable 冻结、performance measurement contract、CPI baseline、
bottleneck census、单机制优化、CPI/PPA 联合资格、系统再认证和可重复 promotion。这里列出的不是
既成成果或项目进度，而是对方法的下一组可证伪条件：若 Workflow 无法使每次裁决绑定当前身份、
使跨轮对象满足版本与 $\operatorname{Ext}_{\theta}$ 约束、阻止越级或为
候选产生可复核反例，它就不能承载下一阶段决策。

当前状态可以精确写成：指定 single-hart RV64 dual-issue OoO cohort 已有
\statusword{ARCH\_STABLE} 和 \statusword{PERF\_BASELINE} 收据；当前基线具有 CoreMark/Dhrystone
重复性和 stats-off 非干扰对照；owner-timing workload 收据因非法身份事件失败关闭；PPA 仍
\statusword{UNQUALIFIED}，\texttt{promotion\_eligible=false}。因此下一步不是根据驻留排序直接改 RTL，
而是先闭合 transaction owner 量测、形成可证伪瓶颈、冻结单机制 candidate 与 guardrail，再进行同身份
CPI/PPA A/B。若修改周期、资源或调度合同，必须重新经过 architecture gate。

该约束还要求把 Linux 首次发现的系统层缺陷下沉到最低充分验证层：软件可见语义优先进入 AM、
架构测试或 DiffTest；逐周期 owner、flush、replay、completion/commit 合同优先进入 TB 与 assertion；
只有设备组合、系统事务与系统性能继续保留在 Linux/Ubuntu 层。如此，Loop-Work 的反馈不仅修复当前
候选，还能形成供后续任务复用的低层检查入口；这些入口能否降低总体验证成本，仍需同预算对照实验。

\section{结论}

本文提出 Loop-Work，把处理器 Agent 的工程能力定义为在固定验收标准下安全闭合任务的能力。控制面
把目标编译为对象、权限和门禁，知识面提供当前任务适用的规则与程序化能力，执行面调用真实编译、
仿真、综合和回放工具，证据面将观测绑定到实验身份、判定器和允许声明。内层闭环处理当前候选，外层
闭环把重复反例固化为规则、Skill、checker、合同或新节点；二者共同把一次生成转换为可恢复、可审查
的工程状态迁移。

该方法在同一仓库中经历了逐级增强的验证压力：RV32 从 lint 进入动态执行，single 扩展到 SoC，NPC
与 NEMU 建立 target/reference 闭合，OpenSBI/Linux 进入 Ubuntu 22.04 系统事务，RV64 双发射 OoO 核
形成 ARCH\_STABLE 与 PERF\_BASELINE。十九小时 A3 的原始 FAIL 与冻结重放并存，23 个目标 mutant
被拒绝，branch speculation 候选被回滚，owner-timing 收据失败关闭，代理 PPA 保持 UNQUALIFIED。
这些结果共同说明，同一四平面接口能够在所列压力层级产生正结果、反例和未晋级状态，而不是只保存
最有利的成功日志。

Loop-Work 的工程价值在于把个人提示经验转化为可版本化的团队接口：模型可以变化，任务仍由合同、
身份和证据责任约束；项目可以扩展，新的系统反例仍能下沉为低成本检查入口。当前单仓库纵向材料支持
方法的可执行性、过程链与声明边界，尚不估计相对其他 Agent 架构的生产率因果增益。后续受控实验将
比较提示、工具反馈、合同化闭环和资格化闭环，并用定向消融分别检验 P1--P4。
