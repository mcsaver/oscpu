# 第 8 章：控制域、pending/drain 与全局冲刷

## 8.1 先区分两类恢复

### OoO recovery

branch mispredict/checkpoint recovery：以某个仍在 ROB 中的 producer 为边界，保留 older，
取消 younger，然后从正确 PC 继续。它是域 A 的正常投机机制。

### Serialized control

ECALL、xRET、WFI、SFENCE、FENCE.I、FENCE、IRQ、architectural trap 和
simulation exit：先建立唯一 pending owner，停止接纳新工作，等待所有 older owner
达到精确 terminal，再应用 side effect。它们是域 B 的 pending/full-drain 路。

CSR 在当前产品配置下是 **split-domain**：合法非 FP 的 head0 CSR 走 ROB queue-head，
以 `head0_csr_inflight` 持续拥有 stop，在队头只等待 `mem_idle` 后 C0 提交；lane1 CSR、
FP CSR 与非法 CSR/其他 SYSTEM 仍由 pending/trap 路处理。不能再把“所有 CSR 都进入
pending holder”当成当前拓扑。

把两者都叫 `flush` 会掩盖最关键的年龄和 owner 区别。

## 8.3 pending SYSTEM 的八种 canonical kind

`OooPendingSystemSequencer` 用一个 `kind_q` 表示：

```text
CSR / ECALL / XRET / WFI / SFENCE_FAMILY / FENCEI / FENCE / IRQ
```

这里的 `CSR` 指仍需 pending 的 lane1/FP CSR（以及显式比较配置下的 CSR），不是当前
产品默认的合法非 FP head0 queue-head CSR。

不能同时用多组 loosely-related valid bits 表示同一个 owner，否则可能出现
`pending_ecall=1 && pending_fence=1`，最后 CSR side effect 和 redirect payload 来自不同种类。

holder 还保存 PC、instruction、CSR addr/data、ProducerId、trap payload 等精确执行所需 facts。
CSR holder 在 ROB admission 后保存完整 ProducerId lease；后续 legality/read-data 刷新
不能退化成“PC 相同就算同一个请求”。

## 8.4 pending transaction 的生命周期

以 lane1/FP CSR 或其他 serialized SYSTEM 为例：

### Ccapture

lane1 barrier 或 pending 类型通过分类和 admission；pending holder 锁存
kind/PC/ProducerId，`stop_pending` 置位。合法非 FP head0 CSR 不走这个 capture。

### Cdrain

前端停止 dispatch；ROB/IQ/EX/memory 中比 pending 老的 transaction 继续完成/退休。
pending 自己不能被更年轻工作越过。

### Cterminal

ROB/issue drained，且 exact memory owner 已 terminal。对于普通 FENCE 还要求 full
`mem_idle`。

### Capply

发出唯一 pending CSR/trap/xRET/fence action，形成 redirect/MMU flush/commit event。

### Cclear

下一个时钟沿清 holder 和 `stop_pending`；无新 capture 时后续周期不得重复 action。

```wavedrom
{
  "signal": [
    {"name": "clk",              "wave": "p.........."},
    {"name": "capture",          "wave": "010........"},
    {"name": "pending_valid",    "wave": "0.1....0..."},
    {"name": "stop_pending",     "wave": "0.1....0..."},
    {"name": "ROB drained",      "wave": "0...1......"},
    {"name": "mem terminalized", "wave": "0....1...."},
    {"name": "apply pulse C0",   "wave": "0....10..."},
    {"name": "clear edge C1",    "wave": "0.....10.."},
    {"name": "repeat C2",        "wave": "0.........."}
  ],
  "head": {"text": "serialized owner：capture -> drain -> exact terminal -> 单次 apply -> clear"}
}
```

图中 `mem terminalized` 和 apply 同期只是示意；真实组合/注册相位以 gate 和 sequencer
端口为准。关键是 C0/C1/C2 exactly-once。

当前 `OooControlEventApplySequencer` 明确把 full-flush request 的 reason/kill-index
锁存一拍：request 在 C0 被接收，apply 在 C1 可见。`OooControlFlushSequencer` 也注册
`core_trap_flush`、`trap_redirect_squash` 和 `checkpoint_mem_flush`，不要在时序图中
把 raw request、apply 与所有目标模块的 flush 画成一个组合脉冲。

### pending 路与 head0 queue-head 路不要混画

| 对比点 | head0 queue-head CSR（产品默认） | pending CSR / SYSTEM |
| --- | --- | --- |
| birth owner | `head0_csr_inflight` + `stop_pending`，CSR 已进 ROB | `OooPendingSystemSequencer` holder + `stop_pending` |
| younger 阻断 | inflight owner 在 CSR 离开 FIFO 后继续保持 | pending holder live 保持 |
| memory 条件 | queue-head CSR 只等 `mem_idle` | pending SYSTEM/trap 看 exact `mem_owner_terminalized`；FENCE 额外看 `mem_idle` |
| 架构动作 | C0 commit/CsrFile request，C1 serial/full-flush apply | drain 完成后由对应 pending terminal/action 执行 |
| 释放 | commit/older kill/C1 reset | exact terminal/clear/squash |

queue-head 路不能改成等待 `mem_retire_quiet`/SQ empty：CSR 后面的 younger Store 尚未
退休，不能从 SQ 排出；若 CSR 又等 SQ empty，就会互相等待。第 7 章的 CSR 专用时序图
把这条活性边界画成 C0/C1/C2。

## 8.5 为什么 ROB empty 还不够

older memory transaction 可能已：

- 离开 IQ；
- ROB entry 已进入特殊 retire/terminal 边界；
- 仍在 MIQ、bridge、PTW、D-cache miss、response reservation 或 SQ drain 中。

因此 `OooPendingDrainResolveGate` 对 pending SYSTEM、architectural trap 和 exit 使用
exact `mem_owner_terminalized`。如果只看 ROB/IQ empty，pending CSR/satp/trap 可能在旧
memory 仍使用旧 privilege/address space 时提前生效。head0 queue-head CSR 另由 ROB 的
`mem_idle` hold 负责，不能拿这段 pending gate 解释它的退休条件。

## 8.6 普通 FENCE、FENCE.I 与 SFENCE 的区别

### FENCE

等待 full memory idle，确保前后 memory ordering；不应产生 CSR/trap/MMU side effect。

### FENCE.I

在精确边界清取指 packet cache/ITLB 相关状态，使同 PC 后续重新 fetch；产生 typed
redirect/MMU pulse。它不能只清前端 FIFO而保留 stale fetch cache line。

### SFENCE.VMA/SINVAL family

刷新地址翻译相关状态，涉及 satp/ASID/VPN 范围语义；当前 control event 以
`SFENCE_FAMILY` kind 统一序列化，再向 IFU/LSU MMU owner发 pulse。

数据侧 `OooMemoryRequestGate` 对 satp/SFENCE/FENCE.I commit 再打一拍形成
`mmu_flush_q`；而 core-local/checkpoint memory flush 可在不同相位可见。因此必须逐个
owner 标注 C0/C1，不能笼统写“控制事件同拍清全核”。

## 8.7 Trap 与 xRET

### Trap

selected trap 写 xEPC/xCAUSE/xTVAL，更新 privilege/interrupt-enable stack，选择 xTVEC
target，然后 redirect。

### xRET

从 xEPC 恢复 PC，按 mstatus/sstatus 恢复 privilege/interrupt-enable stack，产生
redirect。它不是“普通跳转”，因为会改变权限状态。

trap/xRET side effect、target 和 flush 必须属于同一个 typed event。

## 8.8 Architectural trap 与 simulation exit

`OooPendingTrapExitSequencer` 保存 architectural trap 和 simulation exit 的 pending
payload；`OooTrapExitEventMux` 在 exact terminal 形成唯一 raw event；
`OooTrapExitOutputSequencer` 把最终 `trap_valid/exit_valid/halted` 锁成可观测输出。

older trap/recovery 应压制 exit，不能同一 transaction 同时产生 trap 和 exit 两个 terminal。
raw event 应是单拍；sticky output 可以保持，但不能靠 sticky seen-bit 掩盖 raw 重复。

    {"name": "clk",             "wave": "p........"},
    {"name": "pending exit",    "wave": "01...0..."},

    {"name": "raw exit",        "wave": "0........"},

    {"name": "trap_valid sticky","wave": "0...1...."},

## 8.9 lane1 admission

双槽前端可能出现 lane0 普通指令、lane1 SYSTEM/trap。lane1 只有在 lane0 的 barrier/dispatch
关系明确后才能 capture；否则会让 younger SYSTEM 越过尚未接纳的 lane0。

`OooPendingLane1CaptureGate` 负责 lane1 局部分型和 payload；`OooPendingDispatchArbiter`
负责 lane0/lane1/IRQ 等来源的全局 capture 仲裁。

当前 pending branch/jump/memory/FP 历史臂已被拆除或结构性不可达；live 域 B 主要是
SYSTEM/trap/IRQ/exit。看到保留的兼容端口时要结合 parent 常量和实例层次判断，不要把
历史接口当活数据通路。

## 8.10 admission cancellation

pending SYSTEM 不是一旦“组合看见”就必然出生。同拍可能发生更老 branch recovery、
trap flush 或 owner 冲突。`OooPendingSystemAdmissionCancelGate` 统一判断 admission 是否
被更高优先级事件取消。

正确语义：

```text
raw classify != owner birth
owner birth = classify && queue-head accepted && !older cancel
```

如果用 raw lane facts 直接置 `stop_pending`，被 branch kill 的 SYSTEM 会留下 orphan stop，
Core 永久不再运行。

## 8.11 `stop_pending`

`OooStopPendingSequencer` 是停止前端接纳的注册 owner。它只消费：

- 已接受的 pending owner birth/live；
- precise CSR lease；
- queue-head real fire/inflight/kill；
- trap/exit holder；
- C1 clear/reset。

它不应从多个 raw type bit 自行猜 owner。`stop_pending=1` 后，run gate 禁止新 fetch/
dispatch，但 older backend 应继续推进到 drain。

## 8.12 flush 不止一种

| Flush/recovery | 目标 | 保留什么 |
| --- | --- | --- |
| branch younger kill | ROB/IQ/EX/memory younger | branch 及 older |
| core local flush | 当前 speculative core state | 已 commit 架构状态 |
| serial/trap flush | pending 后的 younger state | pending 之前已 commit state |
| MMU flush | ITLB/DTLB/FPC/translation context | 架构 CSR 新状态 |
| memory drop/epoch | 旧 request/response owner | 新 epoch transaction |
| final reset/halt | 全局运行状态 | terminal observable payload |

`OooControlFlushSequencer` 保存 trap/checkpoint 等注册 flush；`OooCoreSliceControlGate`
把多个上游事件合成为执行 slice 可消费的 run/flush/kill。SQ 对 committed 与
speculative entry 的 survive 规则又不同。

## 8.13 Redirect 仲裁

redirect 来源可能包括：

- branch mispredict；
- direct branch/jump/return；
- trap；
- xRET；
- CSR commit；
- SFENCE/FENCE.I；
- architectural fault；
- recovery checkpoint。

`OooRedirectArbiter` 选择唯一 winner。优先级不能只看 event type，还要考虑年龄：
更老 trap 不应被更年轻 branch 覆盖。winner 的 valid/reason/target/source/age 必须同源。

当前组合仲裁先按 ROB 环形年龄选择更老事件；年龄相同时使用
`trap > branch > direct`。它只选择 transaction，不保存 redirect state；实际 PC/flush
何时注册生效，要继续沿 `OooFrontend` sequencer 和 control apply 边界追踪。

## 8.14 observable gate

`OooCoreObservableOutputGate` 把内部 trap/debug/CSR/control 状态投影到顶层稳定观测接口；
`OooTrapExitOutputSequencer` 保存 sticky terminal。观测逻辑不能反向参与功能去重，否则
“checker 看不到重复”会变成设计语义。
