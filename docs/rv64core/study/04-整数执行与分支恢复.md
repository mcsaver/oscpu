# 第 4 章：整数执行与分支恢复

## 4.1 后端层次

当前执行层次是：

```text
OooExecuteBackend
└── OooAluCoreSlice
    ├── OooAluDecodeBackend
    │   ├── DecodeStage ×2
    │   └── OooIntBackend
    └── OooArchRegFile
```

`OooExecuteBackend` 负责把 core glue 的 dispatch/control/memory 边界接到 core slice；
`OooAluCoreSlice` 还放置架构 GPR；真正的整数乱序执行和大部分 completion/memory owner
集中在 `OooIntBackend`。

## 4.2 两个 issue lane 不等于两套完整执行单元

`OooIntBackend` 有：

- 两个普通 ALU；
- branch compare/resolve 路径；
- bitmanip gate；
- 一个 MulDiv 单元；
- 一个 carry-less multiply 单元；
- LSU 地址/数据形成 helper；
- AMO result gate；
- 两个普通 EX completion stage；
- 一个 branch resolve stage；
- FP backend、SQ/LQ/双 MIQ、memory owner 跟踪等下游。

ALU 可以双路并行，但长延迟或专用资源往往只有一份。issue select 必须把“entry ready”
和“资源可接受”同时纳入。

## 4.3 普通 ALU 路径

`ALU` 处理加减、逻辑、移位等基础计算；`WBU` 对写回值做最终选择/整理。RV64 的一个
常见易错点是 W 类指令：

```text
ADDW/SUBW/SLLW/SRLW/SRAW
```

它们先按 32 bit 语义计算，再把 bit31 符号扩展到 64 bit。不能直接使用 64 bit 结果的
低 32 位后零扩展。

普通 ALU transaction 的逻辑周期：

```text
issue fire -> PRF/bypass operand -> combinational ALU
           -> EX PipeStageReg -> global completion arbitration
```

下游 completion slot 忙时，stage valid 必须保持，不能重复产生两个 completion。

```wavedrom
{
  "signal": [
    {"name": "clk",          "wave": "p......."},
    {"name": "issue_valid",  "wave": "01.0...."},
    {"name": "issue_ready",  "wave": "01.0...."},
    {"name": "issue_fire",   "wave": "01.0...."},
    {"name": "ex_valid",     "wave": "0.1..0.."},
    {"name": "wb_ready",     "wave": "0..10..."},
    {"name": "ex_payload",   "wave": "x.=..x..", "data": ["Producer P"]},
    {"name": "complete",     "wave": "0..10..."}
  ],
  "head": {"text": "EX stage 遇 completion 反压时保持同一个 producer"}
}
```

把无停顿最短路径按边沿展开，会更容易看清“组合”和“流水级”的区别：

1. D0 上升沿：dispatch 同时写 RAT、FreeList、Busy、ROB 和 IQ；
2. D1 周期：新 IQ resident 才能被选择，issue→PRF/forwarding→ALU 是组合路径；
3. D1 上升沿：结果进入 EX→WB `PipeStageReg`；
4. D2 周期/边沿：完整 ProducerId 通过 exact-open 授权，写 PRF、清 Busy、写 ROB done；
5. D3 周期：ROB 才能从 edge-old done 状态生成 commit，D3 边沿更新架构 GPR。

```wavedrom
{
  "signal": [
    {"name": "clk",                "wave": "p......"},
    {"name": "dispatch_fire",      "wave": "10....."},
    {"name": "IQ resident",        "wave": "01....."},
    {"name": "issue_fire",         "wave": "010...."},
    {"name": "EX_to_WB_valid",     "wave": "0.10..."},
    {"name": "PRF_ROB_WB_edge",    "wave": "0..10.."},
    {"name": "ROB_commit_visible", "wave": "0...10."},
    {"name": "Arch_GPR_update",    "wave": "0....10"}
  ],
  "head": {"text": "普通整数 ALU：dispatch 后至少跨三个后续上升沿才更新架构 GPR"}
}
```

这是当前 RTL 的无停顿局部最短路径，不是整条程序的固定 latency。ROB 头阻塞、WB 仲裁、
control gate 或下游反压都会继续增加等待。

## 4.4 Compare 与 branch

`CompareUnit` 根据 signed/unsigned 和比较类型生成 taken。branch 还需要：

- 当前 PC；
- B immediate target；
- 实际 fall-through；
- uop 携带的 predicted next PC；
- ProducerId/ROB age；
- BPU update facts。

如果实际 next PC 与 predicted next PC 相同，branch 只完成并更新 predictor；如果不同，
它产生 recovery candidate。

## 4.5 为什么分支要在 issue 级解析

旧式教学核可能在 decode 就判断 branch，但乱序核的源寄存器可能尚未 ready。当前 branch
作为普通 IQ uop：

1. rename 后等待物理源；
2. oldest-ready issue；
3. compare 得到 taken/target；
4. 与 `pred_npc` 比较；
5. 产生 branch completion 和可能的 recovery。

这样 branch 可以真实依赖前序计算，同时不会为“源没准备好”专门冻结整个前端。

当前 branch 只在 **physical issue0** 解析。issue 当拍同时形成 EX0 packet 和 resolve
packet；下一周期 resolve 除了比较 ROB index/generation，还必须与 EX0 保存的完整
ProducerId 一致。这个 coherent check 防止陈旧 resolve 借用已经复用的 ROB 槽。

## 4.6 错预测恢复

错预测发生时必须同时解决“下一条从哪取”和“已错取的年轻状态怎么办”。

### Redirect

branch resolve 进入统一 redirect 仲裁，与 trap、serialized control、direct control-flow
等候选比较年龄/优先级，winner 更新 PC 并处理 outstanding fetch。

### ROB walk

ROB 以 branch 为边界，取消更年轻 entries。每个被取消 entry 可能要求：

- 恢复 rename map；
- 归还新分配的物理寄存器；
- 清 IQ entry；
- kill 尚未完成的 EX/FP transaction；
- drop MIQ/bridge/LQ 中的 younger memory owner；
- SQ 清未 committed younger store；
- 不能清已经 commit 的 store；
- 阻止晚到 response 获得 completion 资格。

“清 ROB valid”只是恢复的一个部分。

错误预测确认的当拍，后端会先组合屏蔽 strictly-younger side effect，分支自己与 older
事务仍可生存；随后 ROB 从 `tail-1` 反向 walk，每拍最多撤销两项。walk 期间 dispatch
和 commit 冻结，但 surviving older writeback 仍需被吸收，否则会丢失已经合法完成的结果。

```wavedrom
{
  "signal": [
    {"name": "clk",                "wave": "p........."},
    {"name": "branch issue",       "wave": "010......."},
    {"name": "branch resolve",     "wave": "0.10......"},
    {"name": "mispredict",         "wave": "0.10......"},
    {"name": "redirect_valid",     "wave": "0..10....."},
    {"name": "younger kill",       "wave": "0..10....."},
    {"name": "fetch outstanding",  "wave": "1...0.1..."},
    {"name": "correct-path fetch", "wave": "0.....10.."}
  ],
  "head": {"text": "branch resolve 后统一 redirect，并取消所有 younger transaction"}
}
```

具体实现可能让某些信号同拍组合有效或下一拍注册生效；读图的重点是 owner 顺序：
旧路径 response 即使晚到，也不能重新进入 FIFO。

## 4.7 Direct branch、BPU 和 RAS

前端对已知 direct JAL、return 和条件 branch 做预测/fast-path，但这些都不能取代后端
真实解析：

- BPU 给出方向；
- branch target helper 给出目标；
- RAS 预测 return target；
- uop 保存预测 next-PC；
- issue resolve 给出 actual next-PC；
- BPU/RAS 更新 gate 只接受有资格的解析事件。

预测状态也是 speculative state。错误路径上的 push/pop/update 不能永久污染后续预测；
因此前端有 branch-spec tracker、direct wait buffer 和 recovery gate。

## 4.8 MulDiv

`OooMulDivUnit` 是长延迟时序 owner。学习重点：

- start 只有在单元 idle 且 issue transaction 真正获准时有效；
- operand、operation 和 ProducerId 必须锁存；
- busy 时新的同资源 uop不能覆盖 owner；
- flush/kill 后旧结果不能继续获得 completion；
- done 可能与 completion slot 反压相遇，需要保存结果资格；
- DIV 除零、signed overflow 和 word operation 有专门结果规则。

长延迟并不意味着 ROB 停住：后面的独立 ALU 指令仍可 issue/complete，只在 commit head
遇到未完成 MulDiv 时停住。

当前状态主线是 `IDLE → REQ_BUF → MUL_RUN/DIV_RUN → RESP`。请求不是组合穿透；
radix-4 主循环每拍处理两位，最大约 32 个迭代拍，除零/溢出等 special case 可从
`REQ_BUF` 快速进入 RESP。RESP 遇全局 completion 反压时必须连同完整 ProducerId 保持。

## 4.9 CLMUL 与 bitmanip

`OooClmulUnit` 实现 Zbc carry-less multiply；它与普通乘法的区别是部分积用 XOR 聚合，
不产生进位。`OooBitmanipGate` 处理 Zba/Zbb/Zbs 中适合组合实现的位操作、计数、旋转、
逻辑变换等。

当前 CLMUL 是固定 64 次 RUN 的独立 FSM，而不是普通 multiplier 的一个 mode。它从
capture 到 RESP 都持有完整 ProducerId，因此 branch kill 必须命中这个 holder，而不只是
清除原 IQ entry。

把 bitmanip 单独抽成 gate 的收益：

- 主 `OooIntBackend` 不必继续膨胀；
- 可清楚看见 opcode 到结果的组合 owner；
- synthesis 可独立观察其逻辑成本；
- testbench 可针对扩展语义做 focused 检查。

## 4.10 AMO gate 与普通 ALU 的区别

`OooAmoGate` 计算 AMO 的“读旧值后写新值”结果，例如 swap/add/xor/and/or/min/max。
但 AMO 的正确性不仅是一个组合函数：

- 地址必须满足自然对齐；
- 读改写需保持原子序；
- LR/SC 还需要 reservation；
- memory owner、SQ drain 和 bridge transaction 要序列化；
- load result 与 store side effect 的完成/退休边界不同。

因此 `OooAmoGate` 只负责数据变换；原子 transaction 的 owner 在
`OooIntBackend` 和 memory path 中。

## 4.11 架构 GPR 为何在 commit 侧更新

`OooArchRegFile` 保存对外可见的 32 个 GPR。执行结果先进入物理寄存器；只有 ROB commit
才写架构 GPR。这样：

- younger 完成结果不会提前暴露；
- exception/branch recovery 可直接丢弃 speculative PRF 版本；
- DiffTest/trace 以 commit 为唯一架构事件；
- `x0` 可持续强制为 0。

它物理上位于 `OooAluCoreSlice`，逻辑上属于退休状态。
