# 第 0 章：学习方法与源码导航

## 0.1 为什么不能按“文件顺序”学习

这套 Core 有 150 个 `vsrc` 文件，其中多数文件遵循“一 module 一文件”，但物理目录并不
等于指令真实经过的线性顺序。例如：

- `OooRob` 放在 `writeback/`，实例却位于 `OooDispatchBackend` 内；
- 架构 GPR 文件 `OooArchRegFile` 放在 `writeback/`，实例却位于
  `OooAluCoreSlice`；
- FP 架构/物理寄存器和 FP IQ 分散在 `regread_bypass/`、`scheduling/`，
  由 `OooFpBackend` 统一装配；
- `CsrFile` 在 `NpcCoreTop`，不在 `OooCoreTopGlue` 内；
- IFU 与数据 memory bridge 在 `NpcCoreTop`，Core 的 rename/issue/execute/control
  则在 `OooCoreTopGlue`。

所以正确的学习单位不是“目录”，而是**事务闭环**。本讲义会反复追踪以下闭环：

```text
取指事务:
PC owner -> IFU request -> ITLB/PTW/PMP -> fetch packet -> FIFO -> dispatch

普通整数事务:
dispatch -> rename/ROB/IQ -> issue/PRF -> execute -> completion -> ROB -> commit

访存事务:
issue -> 地址/属性 -> LQ/SQ/MIQ -> bank bridge -> DTLB/PTW/PMP/PMA/D$ -> response
      -> completion -> ROB -> commit；store 在 SQ/ROB 精确头部 launch，并等 B terminal

串行控制事务:
head classify -> pending owner -> stop frontend -> drain older owners
             -> CSR/trap/xRET action -> redirect/flush -> restart
```

## 0.2 先学会区分四类 RTL

### 纯组合 gate

典型文件：`OooFrontendDispatchGate.v`、`OooAmoGate.v`、
`OooCsrTrapRequestMux.v`。

判断方法：没有 `always @(posedge clk)`；输出只由当前输入决定。它不拥有跨周期状态，
但可能位于很长的组合路径上。理解它时要写出布尔条件和优先级，而不是画“状态机”。

### 时序 owner

典型文件：`OooFetchPacketFifo.v`、`OooRob.v`、`OooStoreQueue.v`、
`OooPendingSystemSequencer.v`。

判断方法：有时钟沿更新的数组、valid bit、head/tail/count、busy 或 pending 寄存器。
理解它时要回答：

- 哪个 fire 创建 entry；
- entry 的完整身份字段是什么；
- 哪些事件更新它；
- completion、commit、kill、flush 谁先谁后；
- 同一拍 enqueue/dequeue 时 count 怎样变化。

### 装配 wrapper

典型文件：`OooFrontend.v`、`OooControlPlane.v`、`OooExecuteBackend.v`、
`OooCoreTopGlue.v`。

wrapper 的价值是定义架构边界。不要因为它端口很多就认为它“一定负责很多行为”；
应先看它例化哪些 owner，再看只有本层才能决定的跨子系统 wire。

### 头文件、事实布局和仿真 checker

`define.v` 保存容量和协议枚举；`OooSlotFacts.v`、`*Facts.vh` 保存 packed
观测布局；`debug/*.sv` 是仿真 checker。它们可能不生成硬件状态，但决定了多个模块
如何共享同一语义，不能当成“辅助文件”跳过。

## 0.3 valid/ready 不只是两个信号

对一个标准握手：

```text
fire = valid && ready
```

必须同时检查三条不变量：

1. `valid=1 && ready=0` 时，producer 必须保持 payload；
2. 只有 `fire=1` 才能认为 transaction 所有权转移；
3. flush/kill 若允许取消等待中的 transaction，必须明确由谁丢弃以及怎样防止旧响应回流。

下面是最小的反压模型。C1 producer 给出 A，consumer 不 ready；A 必须稳定到 C3 的
握手沿之后才能撤销。

```wavedrom
{
  "signal": [
    {"name": "clk",     "wave": "p....."},
    {"name": "valid",   "wave": "01..0."},
    {"name": "ready",   "wave": "0..10."},
    {"name": "payload", "wave": "x=..x.", "data": ["A"]},
    {"name": "fire",    "wave": "0..10."}
  ],
  "head": {"text": "valid/ready 反压：payload 在等待期间保持"}
}
```

读实际代码时，不要只搜索 `valid`。还要搜索：

- `ready` 是组合地回传还是被寄存；
- payload 是直接 wire 还是 entry 中已锁存值；
- `flush_i` 对 valid bit 和 payload 的处理是否一致；
- response 端有没有 epoch、ProducerId 或 owner token 防止认错旧事务。

## 0.4 “阶段”与“队列”是两种不同边界

固定流水阶段寄存器由
[`PipeStageReg.v`](../../../npc/rv64/vsrc/pipeline/PipeStageReg.v) 表达：

- `valid_i && ready_o` 接收新 payload；
- 下游 stall 时保持；
- kill/flush 清 valid；
- ready 可由“当前为空”或“当前项被下游取走”产生。

而 IQ、ROB、MIQ、LQ、SQ 是多 entry 队列。它们允许不同指令停留不同时间，并不对应
一个统一的“第 N 级”。因此本讲义使用：

- **边沿 C0/C1/C2**：描述某个具体 transaction 的相对周期；
- **owner/entry**：描述跨周期身份；
- **fire**：描述所有权转移；
- **stage register**：只在真的有一级寄存器时使用；
- **queue residency**：描述在队列里等待，不把等待周期虚构成流水级。

## 0.5 一条乱序指令至少有三种身份

### 架构身份

PC、原始 instruction、架构 `rs1/rs2/rd`。这是软件能理解的身份。

### 重命名身份

源物理寄存器、目的物理寄存器、旧目的物理寄存器。它解决 WAR/WAW，并为结果旁路和
wakeup 提供索引。

### 生产者身份

当前实现把 ROB raw index 与 generation 组合成 ProducerId。仅用环形 ROB index
会在 wrap 后复用；generation 用来区分“同一个格子的不同时代”。任何 completion、
memory response 或 kill 若只比较 raw index，都可能把旧事务的结果交给新事务。

ProducerId 仍是有限位宽，因此安全性不是“位宽够大就行”，而是：

> 一个仍被任何 IQ、执行级、MIQ、bridge、LQ/SQ、collector 等 holder 引用的
> ProducerId，不能被重新分配。

这也是为什么 `OooMemOwnerTracker`、`OooMemOwnerTerminalCollector` 看起来比普通
教学 CPU 复杂：它们在证明“老 memory owner 真正终止”。

## 0.6 建议的源码阅读动作

面对一个 module，按以下顺序：

1. 看 module 参数，确认容量和位宽来自哪里；
2. 把输入输出按 request、response、control、debug 分组；
3. 搜所有 `always @(posedge clk)`，列出状态 owner；
4. 搜 `assign ... fire`、`valid && ready`；
5. 搜 `flush`、`kill`、`redirect`，写优先级；
6. 搜被例化的子 module；
7. 回到 parent，确认当前实例参数和端口没有把某条路径绑死；
8. 最后看 assertion/checker，理解设计者最怕哪类错误。

不要从巨大 `always` 的第一行开始逐字翻译。先画 owner 和事务，再填组合条件。

## 0.7 目录导航

| 目录 | 学习主题 | 首先寻找的 owner |
| --- | --- | --- |
| `core/` | Core/SoC 装配、CSR 边界 | 顶层实例和 `CsrFile` |
| `frontend/` | PC、packet、预测、dispatch | outstanding、FIFO、RAS、BPU |
| `decode/` | ISA 解码、立即数、RVC、FP 分类 | 多数为纯组合 |
| `rename_allocate/` | RAT/free/busy/dispatch | map、free vector、busy vector |
| `scheduling/` | IQ、wakeup、oldest-ready | IQ entries |
| `regread_bypass/` | PRF/FPR 和 pending operand | register arrays |
| `execute/` | ALU、branch、M/D、FP、后端装配 | execute stage、long-op owner |
| `memory/` | LQ/SQ/MIQ、MMU/cache/AXI | queue entries、bridge FSM |
| `cache/`、`sram/` | packet/data cache 和宏 | tag/data/valid、同步 SRAM |
| `writeback/` | ROB、completion/commit 输出 | ROB entries、arch state |
| `control/` | pending、drain、trap/exit、flush | pending owner、stop、sticky output |
| `bus/` | AXI xbar 与片上设备 | AXI channel state |
| `sim/`、`debug/` | DPI、VirtIO、checker | 仿真状态，不进入综合 Core |
| `common/`、`include/` | packed facts、宏和 ABI | 编码真源 |
